
Это результат пробного моделирования анализа и обработки текста. Числовые характеристики - это частые случаи.

Используйте последовательность из четырёх отдельных заданий.

## Запрос 1. Только инвентаризация

> Не составляй оглавление и не назначай темы главам.  
> Пройди каждый источник независимо и создай реестр его тем.
> 
> Для каждой темы укажи:
> 
> - уникальный ID;
> - точный источник;
> - точную главу/параграф источника;
> - исходное название;
> - нормализованное название;
> - краткое описание границ;
> - статус версии;
> - является ли тема атомарной.
> 
> Если пункт содержит несколько независимо объяснимых понятий, раздели его.
> 
> Отдельно создай списки:
> 
> - JLS;
> - JVMS;
> - Boyarsky 829;
> - Boyarsky 830;
> - Mughal 829;
> - Mughal 830;
> - engineering/framework scope.
> 
> Не объединяй списки и не проектируй структуру.  
> В конце докажи количество обработанных разделов каждого источника и перечисли всё, что не удалось классифицировать.

Критерий приёмки: вы можете выбрать любой пункт любой книги или спецификации и найти его в реестре по точной ссылке.

## Запрос 2. Только нормализация и объединение

После проверки первого результата:

> Используй утверждённые независимые реестры. Не составляй оглавление.
> 
> Создай сводный реестр:
> 
> - объедини эквивалентные темы;
> - сохрани ссылки на все источники;
> - не объединяй темы только из-за близких названий;
> - зафиксируй различия в глубине и версии;
> - выдели темы, присутствующие только в одном источнике;
> - выдели темы без авторитетного источника;
> - найди составные темы, требующие дальнейшей декомпозиции.
> 
> Для каждого объединения объясни основание.  
> Отдельно перечисли спорные объединения и не принимай по ним решение без супервайзера.

Критерий приёмки: количество исходных записей до и после объединения сходится; ни одна запись не исчезла без явного отношения `merged into`.

## Запрос 3. Только дома

После утверждения сводного реестра:

> Не составляй окончательное оглавление.
> 
> Для каждой утверждённой атомарной темы назначь:
> 
> - один теоретический дом;
> - допустимые применения;
> - места, где разрешена только ссылка;
> - потенциальные конфликты;
> - причину выбора дома.
> 
> Проведи проверки:
> 
> - тема без дома;
> - тема с несколькими домами;
> - дом с несовместимыми концепциями;
> - нормативное правило, смешанное с framework application;
> - устаревшая тема без legacy-маркировки;
> - version-dependent тема без версии.
> 
> Не исправляй конфликты молча. Покажи их супервайзеру.

Критерий приёмки: для каждой темы существует ровно одна строка владения, но спорные решения видны до формирования оглавления.

## Запрос 4. Построение оглавления и независимый аудит

Только после утверждения домов:

> Построй оглавление исключительно из утверждённой матрицы.
> 
> Затем выполни независимую проверку:
> 
> 1. Реестр → оглавление: каждый Topic ID должен иметь подраздел.
> 2. Оглавление → реестр: каждый подраздел должен иметь Topic ID.
> 3. Источники → оглавление: каждый пункт каждого источника должен трассироваться.
> 4. Дома → оглавление: номер дома должен существовать.
> 5. Дубли: теория одной темы не должна находиться в двух местах.
> 
> Создай отдельный отчёт с результатами и исключениями.
> 
> Не называй результат готовым, если:
> 
> - существуют темы без трассировки;
> - есть спорные дома;
> - есть составные темы, ошибочно названные атомарными;
> - отсутствуют утверждённые источники;
> - проверка выполнена только поиском ключевых слов.

## Как защититься от формального прохождения проверки

В каждом запросе добавляйте:

> Количество строк, уникальность ID и наличие ключевых слов не являются доказательством полноты.  
> Проверка должна быть содержательной и выполняться по первоисточникам.  
> Не генерируй проверяемый файл и его «независимое подтверждение» из одного набора данных.  
> Покажи отрицательные результаты и незакрытые вопросы.  
> Если результат является черновиком, прямо назови его черновиком.


## Спорные объединения

Спорные объединения нельзя автоматически сливать или просто оставить навсегда отдельными. Для каждой из 249 пар нужен отдельный семантический аудит.

Нужно выполнить следующий подшаг Запроса 2:

1. Прочитать соответствующие фрагменты обоих источников, а не сравнивать только заголовки.
2. Зафиксировать границы каждой темы:
    - что именно объясняется;
    - на каком уровне: язык, JVM, API или инженерная практика;
    - какие предусловия, правила, ошибки и практические задачи входят в раздел.
3. Присвоить паре одно из решений:
    - `MERGE` — одна и та же тема с одинаковыми границами;
    - `MERGE_WITH_SPLIT` — есть общее ядро, но часть материала должна остаться отдельной подтемой;
    - `RELATED` — темы связаны, но не эквивалентны;
    - `KEEP_SEPARATE` — совпадение названий случайное или относится к разным уровням;
    - `DEFER` — источников недостаточно либо сначала требуется декомпозиция.
4. Для `MERGE` определить каноническое название, сохранив все источники и locator.
5. Для `MERGE_WITH_SPLIT` создать атомарные темы и показать происхождение каждой.
6. Обновить:
    - сводный реестр;
    - трассировку;
    - журнал решений;
    - перечень одноисточниковых тем;
    - контрольные показатели.
7. Провести повторный машинный аудит: ни одна исходная запись не должна исчезнуть или попасть сразу в несколько окончательных тем без явного отношения.

Особенно осторожно нужно рассматривать:

- одинаковые заголовки в JLS и JVMS: это часто разные уровни описания;
- разделы JLS о декларации и binary compatibility;
- общие названия вроде `Arrays`, `Classes`, `Annotations`, `Exceptions`;
- темы из разных книг с различной глубиной;
- engineering-закладки без утверждённого источника;
- пары с лексическим сходством, но разными объектами или задачами.

Иными словами, файл `06 — Спорные объединения.md` сейчас является очередью решений, а не законченным результатом. До разбора этих пар нормализацию нельзя считать окончательно утверждённой. Следующим действием должен стать именно семантический аудит этих 249 пар, после которого спорный список должен содержать только обоснованные `DEFER`, а остальные решения — перейти в реестр и журнал.
Для Спорных объединений могут потребоваться pdf версии книг.


## Неразложенные записи

Если возникли неразложенные записи, то их необходимо проанализировать отдельно.
Неразложенные записи записи — не обязательно будущие темы. Каждая такая запись может оказаться:

- контейнером, который распадётся на несколько тем;
- одной темой с неудачным или повреждённым заголовком;
- повтором уже существующих тем;
- навигационным элементом без самостоятельного содержания;
- OCR-ошибкой или записью с ненадёжным locator;
- смесью нескольких уровней: теория языка, API и практическое применение.

Что это означает для результата Запроса 3:

- M семантическому кластеру можно назначить предварительные дома.
- Нельзя утверждать, что эти дома покрывают всё содержание пяти источников.
- После разложения N записей появятся новые атомарные темы и новые конфликты владения.
- Некоторые существующие темы могут получить дополнительные источники, уточнённые границы или быть разделены.
- Нагрузка домов и выводы о полноте будут преждевременными.
- Проверка «для каждой темы ровно одна строка владения» будет формально выполнена только для уже утверждённого подмножества, а не для всего материала.
- Построенное затем оглавление пришлось бы существенно пересматривать.

Главный риск — не просто пропустить несколько подразделов. Контейнер `Collections`, `Concurrency`, `Security` или `Testing` может скрывать десятки атомарных тем. Пока контейнер не разложен, невозможно доказать ни полноту, ни отсутствие неправильных домов.

Перед Запросом 3 нужно провести промежуточный этап — декомпозицию N записей:

1. Разделить их по причине:
    - `CONTAINER`;
    - `NEEDS_CONTENT_SPLIT`;
    - `LOCATOR_REPAIR`;
    - `OCR_DAMAGE`;
    - `NAVIGATION_ONLY`;
    - `POSSIBLE_DUPLICATE`.
2. Для контейнеров и составных разделов прочитать фактическое содержание источника.
3. Получить атомарные дочерние темы с собственными source locator.
4. Для каждой исходной записи сохранить отношение:
    - `EXPANDED_TO`;
    - `DUPLICATE_OF`;
    - `NAVIGATION_ONLY`;
    - `REPAIRED_AS`;
    - `DEFER`.
5. Пропустить новые темы через нормализацию и семантическое сравнение с существующими M кластерами.
6. Повторить аудит сходимости:
    - ни одна запись не потеряна;
    - все содержательные элементы имеют атомарное представление;
    - контейнеры не выданы за темы;
    - одна тема не размножена из-за разных формулировок.
7. Только после этого зафиксировать утверждённый вход для Запроса 3.
