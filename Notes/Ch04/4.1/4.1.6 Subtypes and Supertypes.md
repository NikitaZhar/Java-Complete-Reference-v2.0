# 4.1.6 Subtypes and Supertypes

Подтипирование — это отношение «где одно можно подставить вместо другого». Если `B` — подтип `A` (пишут `B <: A`), то значение `B` разрешено использовать в любом контексте, ожидающем `A`, без нарушения типобезопасности; `A` при этом надтип `B`. На этом отношении держатся наследование, интерфейсы, полиморфизм и совместимость при присваивании. По формулировке Mughal, подтип — это *более узкий*, специализированный тип по отношению к своему надтипу. Здесь — само отношение, его формальные свойства и все его источники (примитивы, классы/интерфейсы, массивы, обобщения, null-тип). Механику преобразований по иерархии (upcast/downcast, контексты) см. Ch. 5, полиморфную диспетчеризацию по классу времени выполнения — [[4.1.5 Static vs Runtime Type]], полную теорию обобщений — Ch. 20.

## Formal properties of the relation

Отношение строится из **прямого надтипа** (direct supertype, обозначается `>₁`): это «один шаг» вверх — `B extends A` даёт `A >₁ B`. Само подтипирование `<:` — это **рефлексивное и транзитивное замыкание** прямого отношения:

- **рефлексивность**: `T <: T` — любой тип подтип самого себя;
- **транзитивность**: если `S <: T` и `T <: U`, то `S <: U` (подстановка работает сквозь всю цепочку);
- **собственный подтип** (proper subtype): `S <: T` при `S ≠ T` — то есть строго ниже по иерархии.

Практическое следствие рефлексивности — identity-преобразование (тип в себя) всегда допустимо; транзитивности — `Integer` подставим туда, где ждут `Object`, хотя между ними есть `Number`.

## Primitive subtyping

Подтипирование есть и между примитивами (JLS §4.10.1) — именно оно стоит за неявным расширяющим преобразованием (widening primitive, дом — Ch. 5). Прямые отношения складываются в цепочку:

```java
byte <: short <: int <: long <: float <: double
char <: int
```

```java
char c = 'A';
int code = c;   // char <: int — неявно
long l = code;  // int <: long
double d = l;   // long <: … <: double
```

Две тонкости, которые регулярно подводят. Первая: у `char` единственный прямой надтип — `int`; `char` **не** связан подтипированием с `short` или `byte`, хотя все они «16 бит и меньше». Поэтому `byte → char` не является расширением и требует приведения:

```java
byte b = 1;
// char bad = b;   // compile-time error: byte не подтип char (possible lossy conversion)
```

Вторая: `boolean` не состоит в отношении подтипа ни с чем, кроме самого себя, — он полностью изолирован от числовой иерархии.

## Reference subtyping: classes and interfaces

Для ссылочных типов Java **номинальна**: подтип класса/интерфейса возникает из явной декларации `extends`/`implements`, а не из совпадения структуры. Одинаковый набор полей и методов ничего не значит без объявленного отношения.

```java
class Point { int x, y; }
class Pixel { int x, y; }   // та же форма

Point p = new Pixel();      // compile-time error: Pixel не подтип Point
```

Это «только из деклараций» относится именно к классам и интерфейсам в базовом случае; у подтипирования есть и другие источники (ниже — массивы, обобщения, null-тип), не сводящиеся к `extends`/`implements`. Источники отношения для ссылочных типов:

Наследование класса — `class B extends A` даёт `B <: A`. Реализация интерфейса — `class C implements I` даёт `C <: I`. Корень иерархии — `Object` надтип всех ссылочных типов, включая массивы и интерфейсы. Подстановка подтипа вместо надтипа (upcast) неявна и всегда безопасна; обратный переход (downcast) требует явного приведения и проверяется в runtime.

```java
Number n = Integer.valueOf(5); // Integer <: Number (upcast, без приведения)
Object o = n;                  // Number <: Object (транзитивно)

class Deer {}
class Reindeer extends Deer {}
Deer d = new Reindeer();       // upcast — неявно
Reindeer r = (Reindeer) d;     // downcast — нужен каст; выполнится, тип совпал
Deer plain = new Deer();
Reindeer bad = (Reindeer) plain; // компилируется, но ClassCastException в runtime
```

## Array subtyping

Массивы **ковариантны**: если `S <: T` (ссылочные типы), то `S[] <: T[]`. Кроме того, надтипами **любого** массива (включая массивы примитивов) являются `Object`, `Cloneable` и `java.io.Serializable`.

```java
String[] ss = { "a" };
Object[] os = ss;        // String[] <: Object[] — ковариантность
Object obj = ss;         // массив <: Object
```

Ковариантность удобна, но небезопасна при записи: статический тип переменной `Object[]` разрешает положить любой `Object`, а фактический массив остаётся `String[]`. Компилятор пропускает, JVM ловит в runtime (пример Boyarsky с тем же механизмом):

```java
os[0] = 42;              // компилируется, но ArrayStoreException в runtime
```

Важная граница: ковариантность работает только по **ссылочным** компонентам. Массивы примитивов между собой подтипами не являются, хотя сами примитивы связаны расширением:

```java
int[] ia = { 1 };
// long[] la = ia;       // compile-time error: int[] не подтип long[]
```

## Generic type forms: invariance and the boundary notions

В отличие от массивов, параметризованные типы **инвариантны**: `List<String>` не является ни подтипом, ни надтипом `List<Object>`, хотя `String <: Object`. Так язык закрывает дыру, которую у массивов оставляет ковариантность (Mughal прямо называет это «отсутствием ковариантности подтипов у параметризованных типов»).

```java
List<String> ls = new ArrayList<>();
// List<Object> lo = ls;   // compile-time error: обобщения инвариантны
```

При этом у `List<String>` всё же есть надтипы — но по другим осям, и их полезно назвать как границу (полная теория — Ch. 20):

- **wildcard-надтипы**: `List<String> <: List<? extends String> <: List<?>`. Сам `List<?>` — надтип любого `List<…>`.
- **raw-надтип**: «сырой» `List` — надтип `List<String>` (присваивание в обратную сторону даёт unchecked-предупреждение).
- **корень**: любой параметризованный тип `<: Object`.
- **надтипы типовой переменной** `T` — это её границы: для `<T extends Number & Comparable<T>>` надтипы `T` суть `Number`, `Comparable<T>` и `Object`. Несколько границ задают **intersection type** `Number & Comparable<T>`.

```java
List<String> ls = new ArrayList<>();
List<?> any = ls;          // List<String> <: List<?>
Object obj = ls;           // и <: Object
```

Гибкость, которую отнимает инвариантность, возвращают wildcards (`? extends T` для чтения, `? super T` для записи — PECS); полный разбор в Ch. 20.

```java
List<? extends Number> nums = new ArrayList<Integer>(List.of(1, 2));
Number first = nums.get(0); // читать можно: элемент заведомо Number
nums.add(null); // null допустим как значение любого ссылочного типа
// nums.add(1);             // compile-time error: конкретный элемент — нельзя
nums.remove(0);             // структурная операция без значения неизвестного типа — можно
```

То есть `? extends` — это **не** «только чтение»: нельзя лишь добавить конкретное ненулевое значение (захваченный тип элемента неизвестен); `null`, удаление, `clear` и чтение остаются доступны. «Только чтение» — огрублённая мнемоника PECS, не точное правило.

## The null type as the bottom

Особый **null-тип** — подтип всех ссылочных типов (нижний элемент иерархии ссылок). Поэтому `null` присваивается переменной любого ссылочного типа и ни одной примитивной.

```java
Runnable r = null;   // null-тип <: любой ссылочный тип
```

## Least upper bound — one note

Наименьшая верхняя граница (`least upper bound, lub`) нужна при определении общих надтипов и в выводе типов; общий надтип не обязательно `Object`. Однако тип условного выражения зависит от его категории. Если `integer` имеет тип `Integer`, а `dbl — Double`, выражение `cond ? integer : dbl` является числовым и имеет тип `double` после распаковки и продвижения. Процедура lub — Ch. 20, правила ?: — Ch. 15.

## Common Mistakes

- Полагаться на ковариантность массивов при записи.

```java
Number[] a = new Integer[3];
a[0] = 3.14;   // компилируется, но ArrayStoreException в runtime
```
  Правильно: не смешивать фактический компонентный тип массива с типом переменной; при необходимости — `List<Integer>` вместо `Integer[]`.

- Переносить интуицию массивов на обобщения и ждать ковариантности.

```java
List<Integer> ints = new ArrayList<>();
// List<Number> nums = ints;   // compile-time error
```
  Правильно: `List<? extends Number>` для чтения или `List<? super Integer>` для записи (PECS, Ch. 20).

- Считать `? extends` «списком только для чтения» и удивляться, что `add(x)` не компилируется, а `add(null)` — да. Правильно: запрещено добавлять лишь конкретное ненулевое значение неизвестного элемента-типа.

- Ждать расширяющего преобразования `byte` в `char`: его нет. Для обычной переменной потребуется явное преобразование; в `assignment context` представимая константа может присваиваться char без каста. Например, `final byte b = 1; char c = b;` допустимо. Полные правила — Ch. 5.
