# 4.2.4 int

`int` — 32-битный знаковый целочисленный тип и рабочая лошадь целочисленной арифметики в Java: индексы, счётчики, размеры коллекций, результаты большинства вычислений. Общая механика целых (представление, переполнение, промоушены, сдвиги) описана в [[4.2.1 Integral Types]]; здесь — что специфично именно для `int`: почему он тип по умолчанию, где его диапазона хватает, а где нет.

## Why int is the default integer

Когда вы пишете целочисленный литерал без суффикса — `42`, `1_000_000` — его тип `int`. Это не случайность: `int` совпадает с «естественной» шириной, с которой работает операндный стек JVM, и именно к `int` продвигаются `byte`, `short`, `char` перед арифметикой (см. [[4.2.1 Integral Types]]). Поэтому `int` — выбор по умолчанию: он не требует ни суффикса, ни приведений, ни продвижений, а на современном железе 32-битная арифметика не медленнее более узкой. Более узкие `byte`/`short` берут не ради скорости, а ради компактности при массовом хранении.

Диапазон `int` — от −2 147 483 648 до 2 147 483 647, то есть примерно ±2,1 млрд. Для счётчиков и индексов этого с запасом; ловушки начинаются там, где значение или промежуточный результат тихо выходит за эти границы.

## When int is not enough

Перерасти `int` легко и незаметно, потому что переполнение молчит (см. [[4.2.1 Integral Types]]). Типичные случаи, где нужен `long`:

Время в миллисекундах. `System.currentTimeMillis()` возвращает `long` именно потому, что миллисекунды с 1970 года давно не помещаются в `int`. Хранить их в `int` — это знаменитая «проблема 2038 года».

Идентификаторы и счётчики больших объёмов — автоинкрементные ключи БД, счётчики событий: 2,1 млрд достигается быстрее, чем кажется.

Размеры и смещения больше 2 ГиБ — длины файлов, позиции в них. `File.length()` и каналы возвращают `long`; `int`-индекс массива, кстати, и ограничивает массивы Java длиной примерно до 2³¹ элементов (около 2,1 млрд).

```java
long start = System.currentTimeMillis(); // long не случайно
long id = 3_000_000_000L;                // суффикс L обязателен: 3_000_000_000 не влезло бы в int
// int bad = 3_000_000_000;              // compile-time error: integer number too large
```

Отдельная тонкость — деление `int` усекается к нулю, а не округляется; это не переполнение, а определённое поведение, о котором забывают:

```java
int avg = (1 + 2) / 2;   // 1, а не 1.5 — целочисленное деление отбрасывает дробную часть
double d = 1 / 2;        // 0.0! деление int/int даёт 0, потом уже приведётся к double
double ok = 1.0 / 2;     // 0.5 — хотя бы один операнд должен быть вещественным
```

## The Integer wrapper

Объектная обёртка `int` — `Integer`; она нужна для коллекций и generics и допускает `null`. Переход примитив↔обёртка (autoboxing) разобран в [[4.2.13 Boxing and Unboxing]]. Здесь важно помнить один специфичный для `Integer` подвох: кэш маленьких значений и сравнение `==` — но его дом [[4.1.8 Common Pitfalls]] и Ch. 49, сюда он вынесен ссылкой, а не пересказом.

Литеральные формы `int` (десятичные, `0x…`, `0b…`, `0…`, разделитель `_`) — тема Ch. 3.10; здесь они не повторяются.

## Common Mistakes

- Ждать, что `int`-выражение «дотянется» до `long` само, если присвоить результат в `long`.

```java
long ms = 24 * 60 * 60 * 1000 * 1000; // всё считается в int и переполняется ДО присваивания
```
  Правильно: увести в `long` хотя бы один операнд — `24L * 60 * 60 * 1000 * 1000`.

- Полагать, что целочисленное деление округляет.

```java
int rate = 95 / 100 * 100;   // 0: 95/100 = 0, потом *100
```
  Правильно: менять порядок (`95 * 100 / 100`) или считать в вещественном типе, если нужна дробь.

- Хранить время/идентификаторы в `int`. Правильно: `long` для эпохи-миллисекунд, крупных ID и размеров.
