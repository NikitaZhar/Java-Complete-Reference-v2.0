# 4.2.7 Floating-Point Types

Вещественных типов два: `float` (32 бита) и `double` (64 бита), оба по стандарту IEEE 754. Это точка, где интуиция «числа как в математике» перестаёт работать: вещественные значения приближённы, у них есть `NaN` и бесконечности, а привычные операции ведут себя иначе, чем у целых. Здесь собрана механика, общая для обоих типов; специфика и выбор между ними — [[4.2.8 float]] и [[4.2.9 double]].

## Why decimals are not exact

IEEE 754 хранит число как двоичную дробь: знак, показатель степени двойки и мантисса. Многие привычные десятичные дроби в двоичной системе периодичны и в конечное число бит не укладываются — ровно как `1/3` не записать конечной десятичной дробью. Поэтому `0.1`, `0.2`, `0.3` хранятся приближённо, и арифметика над ними накапливает погрешность.

```java
System.out.println(0.1 + 0.2);          // 0.30000000000000004, а не 0.3
System.out.println(0.1 + 0.2 == 0.3);   // false
```

Это не баг Java и не ошибка процессора — это фундаментальное свойство двоичного представления, одинаковое во всех языках с IEEE 754. Практический вывод: **вещественные типы нельзя использовать для денег и любых точных десятичных расчётов**. Для денег берут целые в минимальных единицах (копейки, центы) или `BigDecimal` с явным масштабом и округлением — его дом Ch. 49/50, сюда вынесен ссылкой.

Полезно различать **точность** (сколько значащих бит, ≈7 десятичных цифр у `float`, ≈15–16 у `double`) и **величину** (какой диапазон, до ≈3.4·10³⁸ у `float`, ≈1.8·10³⁰⁸ у `double`) — Mughal подчёркивает, что это разные вещи: расширение `long → float` не выходит за диапазон, но может потерять младшие значащие биты.

## Formats and finite boundaries

float соответствует binary32: 1 бит знака, 8 бит экспоненты и 23 явных бита дробной части. У нормальных значений точность составляет 24 двоичных разряда с учётом неявного ведущего бита. У double (binary64) — 1, 11 и 52 бита соответственно, 53 разряда точности. Это форматы значений, а не физический размер переменной в конкретном объекте.

MIN_VALUE у Float и Double — наименьшее положительное ненулевое значение, а не самое отрицательное. MIN_NORMAL — наименьшее положительное нормальное значение. Между нулём и MIN_NORMAL существуют субнормальные значения; их относительная точность постепенно уменьшается. Самое отрицательное конечное значение — -MAX_VALUE. Отдельно существуют оба знаковых нуля, бесконечности и NaN.

```java
System.out.println(Float.MIN_VALUE > 0);                 // true
System.out.println(Float.MIN_VALUE < Float.MIN_NORMAL);  // true
System.out.println(16_777_216f == 16_777_217f);            // true
System.out.println(9_007_199_254_740_992d ==
                   9_007_199_254_740_993d);              // true
```

Последние равенства показывают ограничение точности: соседние математические целые могут округлиться к одному представимому значению. Основные арифметические операции округляют к ближайшему представимому результату; при равном расстоянии выбирают вариант с чётным младшим разрядом (ties-to-even). Преобразование в целые, % и специальные API-операции имеют отдельные правила — Ch. 5 и Ch. 15.


## Comparing floating-point values

Сравнивать вещественные на точное равенство `==` **опасно после неточных вычислений**: два «равных по смыслу» результата отличаются в младших битах, и `==` вернёт `false`. Но это не абсолютный запрет: точное `==` законно и уместно для значений, которые представимы точно и не прошли через неточную арифметику, — проверка на `0.0`, на конкретный sentinel, на бесконечность, сравнение точно заданных констант.

```java
double d = readMeasurement();
if (d == 0.0) { }                 // ок: ноль представим точно
if (d == Double.POSITIVE_INFINITY) { } // ок: точная проверка на бесконечность
if (0.1 + 0.2 == 0.3) { }         // почти всегда НЕ то: результат неточной арифметики
```

Когда сравнивают именно **результаты вычислений**, нужен допуск (tolerance), и здесь распространённый рецепт `Math.abs(a - b) < 1e-9` **не является универсально правильным** — фиксированный абсолютный порог ошибается в обе стороны в зависимости от масштаба:

```java
// у нуля: разные числа объявляются «равными»
System.out.println(Math.abs(1e-10 - 2e-10) < 1e-9);   // true — а числа отличаются вдвое
// на больших величинах: относительно равные объявляются «разными»
double a = 1e8, b = 1e8 + 0.05;
System.out.println(Math.abs(a - b) < 1e-9);           // false — хотя относительно почти равны
```

Правильнее выбирать стратегию под задачу: **абсолютный** допуск — рядом с нулём; **относительный** (порог, умноженный на масштаб операндов) — для больших величин; **ULP-ориентированный** (`Math.ulp`) — когда важна близость «в единицах последнего разряда».

```java
static boolean nearlyEqual(double a, double b, double relEps) {
    return Math.abs(a - b) <= relEps * Math.max(Math.abs(a), Math.abs(b));
}
```

И даже это не панацея: разность может **переполниться** (`-Double.MAX_VALUE - Double.MAX_VALUE` даёт `-Infinity`, `Infinity - Infinity` — `NaN`), у бесконечностей разность не определена, а `NaN` требует отдельной политики (см. ниже). Порог зависит от домена, и единого «правильного» epsilon не существует.

## NaN and infinities: floating-point does not throw

У вещественных типов есть значения, которых нет у целых, и это меняет поведение при «недопустимых» операциях. Деление на ноль у целых бросает `ArithmeticException` — а у вещественных **не бросает ничего**, возвращая специальное значение:

```java
System.out.println(1.0 / 0.0);   // Infinity
System.out.println(-1.0 / 0.0);  // -Infinity
System.out.println(0.0 / 0.0);   // NaN (не число)
```

`NaN` — «не число» (Not a Number) — результат неопределённых операций (`0.0/0.0`, `Math.sqrt(-1)`). Точное правило сравнений с `NaN` (Mughal): числовые операторы `==`, `<`, `<=`, `>`, `>=` с `NaN` дают `false` — включая `NaN == NaN`; а `!=` даёт `true`. Отсюда знаменитое «`NaN` не равен ничему, даже себе».

```java
double nan = 0.0 / 0.0;
System.out.println(nan == nan);        // false
System.out.println(nan != nan);        // true  — это корректный тест на NaN
System.out.println(nan < 1.0);         // false — любое отношение с NaN ложно
System.out.println(Double.isNaN(nan)); // true  — самый читаемый способ
```

Практический вывод: тестов на `NaN` два равноправных по корректности — идиома `x != x` и `Double.isNaN`/`Float.isNaN`; в коде предпочитают `isNaN` как более читаемый, но `== NaN` не работает никогда (всегда `false`). Ещё тонкость представления — **знаковый ноль**: `0.0` и `-0.0` различны в битах, и `1.0/0.0` даёт `+Infinity`, а `1.0/-0.0` — `-Infinity`, хотя `0.0 == -0.0` истинно.

## Overflow and underflow

При выходе за конечный диапазон `overflow` может дать `±Infinity`. `Underflow` связан с очень малыми по модулю результатами: они могут стать субнормальными, с меньшей относительной точностью, а затем округлиться до знакового нуля. Это не то же самое, что потеря значащих цифр при вычитании близких чисел.

```java
System.out.println((float) 1e300);   // Infinity — 1e300 вне диапазона float
System.out.println(1e-300 * 1e-300); // 0.0 — underflow
```

## double is the default; float needs a suffix

Вещественный литерал без суффикса — `double`; чтобы получить `float`, нужен суффикс `f` (или `F`). `float→double` расширяется неявно, обратное сужение требует приведения и теряет точность.

```java
double d = 3.14;        // double по умолчанию
float f = 3.14f;        // f обязателен
// float bad = 3.14;    // compile-time error: double не влезает в float без приведения
double back = f;        // ок: float → double, расширение
```

Значения по умолчанию — `0.0` и `0.0f` ([[4.2.14 Default Values and Initialization]]). Обёртки — `Float` и `Double` ([[4.2.13 Boxing and Unboxing]]).

## Common Mistakes

- Хранить деньги в `double`.

```java
double price = 0.10, paid = 0.30;
double change = paid - price * 3;   // не ровно 0.0 из-за погрешности
```
  Правильно: целые копейки/центы или `BigDecimal` (Ch. 49/50).

- Объявлять фиксированный `1e-9` «правильным» сравнением. Правильно: выбирать абсолютный/относительный/ULP-допуск под масштаб задачи; помнить про overflow разности, бесконечности и отдельную политику для `NaN`.

- Проверять `NaN` через `==`.

```java
if (x == Double.NaN) { }   // всегда false — ветка мертва
```
  Правильно: `Double.isNaN(x)` (или, как идиома, `x != x`).

- Ждать исключения при делении вещественного на ноль. Правильно: помнить про `Infinity`/`NaN` и проверять их (`Double.isInfinite`, `Double.isNaN`), иначе «заражённое» `NaN` тихо разойдётся по всем последующим вычислениям.
