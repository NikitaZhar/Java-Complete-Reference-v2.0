# 4.1.5 Static vs Runtime Type

У выражения ссылочного типа различают **статический тип**, известный компилятору, и, если значение не null, **исполняемый тип (runtime type)** — фактический класс объекта. Компилятор проверяет допустимость операций по статическому типу. Выбор переопределения экземплярного метода зависит от фактического класса; перегрузка, поля и static-методы разрешаются статически. Поэтому переменная типа Number может обозначать Integer, но не получает все методы Integer. Примитивное значение не является объектом и не имеет runtime-класса; его формат и допустимые операции задаёт примитивный тип выражения.

## What each type decides

Статический тип решает, что вообще **можно написать**: какие методы и поля доступны, какая перегрузка выбрана, совместимо ли присваивание. Исполняемый тип решает, что **фактически произойдёт** при вызове переопределённого метода.

```java
Number n = Integer.valueOf(5);
// статический тип n — Number: компилятор разрешит только методы Number
long v = n.longValue();  // ок
// n.compareTo(5); // compile-time error: метода нет в Number, хотя Integer реализует compareTo(Integer)
System.out.println(n.getClass()); // class java.lang.Integer — фактический тип
```

## Polymorphism: dispatch by the object's type

Когда подтип переопределяет метод, вызывается версия фактического типа объекта — независимо от того, каким типом объявлена переменная. Классический пример: переменная типа `Deer`, объект типа `Reindeer`.

```java
class Deer {
    public boolean hasHorns() { return false; }
}
class Reindeer extends Deer {
    @Override public boolean hasHorns() { return true; }
}

Deer d = new Reindeer();      // reference type: Deer, object type: Reindeer
System.out.println(d.hasHorns()); // true — вызывается переопределение из Reindeer
```

Перегрузка и доступ к полям разрешаются по статическому типу, а не по фактическому классу. Правила объявления и переопределения методов — Ch. 8, разрешение вызова — Ch. 15; Ch. 41 даёт дополнительный разбор экзаменационных ловушек.

## Casting: allowed by the static type, checked at runtime

Статические типы определяют допустимость приведения по правилам casting context (Ch. 5), а фактический класс определяет успех требуемой runtime-проверки. Отношение подтипа — распространённый случай, но не универсальное условие: некоторые приведения между интерфейсными типами разрешены и без такого отношения.

```java
Number n = Double.valueOf(3.14);
Integer i = (Integer) n;   // компилируется (Integer <: Number), но:
                           // ClassCastException: Double cannot be cast to Integer
```

Массивы добавляют свою проверку: из-за ковариантности присваивание компилируется, а компонентный тип проверяется JVM при записи (см. Ch. 13, ArrayStoreException).

```java
Object[] arr = new String[1]; // ок: String[] <: Object[]
arr[0] = 42;                  // ArrayStoreException в runtime
```

## Run-time type information: instanceof and getClass

JVM хранит фактический тип каждого объекта, и его можно безопасно проверить перед приведением. Современная форма — `instanceof` с pattern matching, которая совмещает проверку и приведение.

```java
Object obj = "hello";
if (obj instanceof String s) {          // проверка + связывание переменной s
    System.out.println(s.toUpperCase()); // HELLO — без ручного приведения
}

Class<?> actual = obj.getClass();       // фактический тип во время выполнения
```

Разница между `instanceof` и сравнением `getClass()`: первый истинен и для подтипов, второй требует точного совпадения класса — это важно при написании `equals` (см. Ch. 49).

## Generics erase, so the runtime type loses parameters

При стирании параметризации одного generic-класса не получают отдельных runtime-классов. Но `List<String>` и `List<Integer>` — статические типы: их объекты могут иметь разные классы реализации, например `ArrayList` и `LinkedList`. Проверка `instanceof` не исследует фактические типы всех элементов. Подробности — Ch. 20.

```java
List<String> list = new ArrayList<>();
System.out.println(list.getClass()); // class java.util.ArrayList — без <String>
System.out.println(list instanceof List<String>); // true: проверка допустима из статического List<String>
Object unknown = list;
// boolean bad = unknown instanceof List<String>; // compile-time error: требовалась бы unchecked-проверка
```

## Common Mistakes

- Ждать, что объявленный тип переменной изменит поведение переопределённого метода.

```java
Deer d = new Reindeer();
// «раз тип Deer — значит hasHorns() вернёт false»  — неверно
```
  Правильно: поведение переопределённого метода задаёт фактический тип объекта (`Reindeer` → `true`).

- Приводить без проверки, полагаясь на то, что «код же скомпилировался».

```java
Object o = List.of(1, 2);
String s = (String) o;   // ClassCastException
```
  Правильно: проверять `instanceof` перед приведением или не терять точный тип.
