На третьем шаге лексической трансляции ([[3.2 Lexical Translations]]) поток входных символов и терминаторов строк сворачивается во входные элементы (input elements), а те из них, что не являются пробелами и комментариями, — это токены. Токены — терминальные символы синтаксической грамматики ([[2.3 The Syntactic Grammar]]): именно с ними работает разбор, ничего не зная о том, как они собраны из символов. Этот раздел задаёт каталог видов токенов и правила разрешения неоднозначностей при их выделении; сами виды детализируются в 3.6–3.12.

## Input Elements and the Five Kinds of Token

```
Input:         {InputElement} [Sub]
InputElement:  WhiteSpace | Comment | Token
Token:         Identifier | Keyword | Literal | Separator | Operator
Sub:           символ ASCII SUB (\u001A, control-Z)
```

Входной элемент — это пробел ([[3.6 White Space]]), комментарий ([[3.7 Comments]]) или токен. Пробелы и комментарии отбрасываются, а пять видов токенов — идентификаторы ([[3.8 Identifiers]]), ключевые слова ([[3.9 Keywords]]), литералы ([[3.10 Literals]]), разделители ([[3.11 Separators]]) и операторы ([[3.12 Operators]]) — передаются синтаксическому анализатору.

Пробелы и комментарии не бесполезны: они разделяют токены, которые иначе слиплись бы. Десять символов `staticvoid` образуют один идентификатор, а `static void` (с пробелом) — два ключевых слова.

```java
int a=1,b=2;
int c = a-=b;   // токены: c, =, a, -=, b  → -= склеивается без пробела
int d = a- =b;  // ошибка компиляции: '- =' не оператор, пробел разорвал -=
```

Как особая уступка ряду ОС, символ SUB (`\u001A`, control-Z) игнорируется, если он последний в потоке.

## Resolving Tokenization Ambiguities

Свёртка неоднозначна: одну и ту же цепочку символов иногда можно свернуть по-разному. Неоднозначности разрешаются фиксированными правилами:

Последовательность, которую можно свернуть и в идентификатор, и в литерал, всегда сворачивается в литерал. Последовательность, которую можно свернуть и в идентификатор, и в зарезервированное ключевое слово ([[3.9 Keywords]]), всегда сворачивается в ключевое слово. Последовательность, совпадающая с контекстным ключевым словом, разбирается по контексту (см. [[3.9 Keywords]]). И отдельное правило для `>`: в контексте типа символ `>` всегда сворачивается в оператор сравнения, даже если рядом стоит ещё один `>`.

```java
List<List<String>> x = new ArrayList<>();   // >> — это два закрывающих угла, не оператор сдвига
int shifted = 1024 >> 2;                     // здесь >> — оператор сдвига (не в контексте типа)
```

Без правила про `>` запись `List<List<String>>` разобралась бы как оператор сдвига `>>`, а `List<List<List<String>>>` — как `>>>`; для четырёх и более `>` токенизация стала бы неоднозначной. Правило снимает это: в типовом контексте углы никогда не склеиваются. Семантика операторов сдвига — Part I, Ch. 15 (Expressions and Operators); сами дженерики — Part I, Ch. 20.

## Left and Right

Спецификация вводит соглашение: если токен `x` предшествует токену `y` в потоке, то `x` находится слева от `y`, а `y` — справа от `x`, независимо от их расположения в двумерном тексте. Это позволяет говорить «правый операнд бинарного оператора» или «левая часть присваивания» безотносительно переносов строк.
