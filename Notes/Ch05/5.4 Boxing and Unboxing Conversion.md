# 5.4 Boxing and Unboxing Conversion

Восемь примитивных типов и их классы-обёртки (`int`/`Integer`, `double`/`Double`, `boolean`/`Boolean` и т. д.) — два представления одних и тех же значений: одно живёт «плоско», другое — объектом. Преобразования между ними называются **упаковкой (boxing)** — примитив → обёртка — и **распаковкой (unboxing)** — обёртка → примитив; неявные их формы зовут авто-упаковкой и авто-распаковкой. Это дом темы: и зачем обёртки нужны, и как работает механизм упаковки, и как он ведёт себя в контекстах преобразования. Устройство обёрток как ссылочных типов затронуто в [[4.3 Reference Types and Values]], контракт `equals`/`hashCode` и кэш — в Ch. 49; всё остальное про boxing/unboxing — здесь. Ключевой факт, вокруг которого крутятся почти все ошибки: упаковка безопасна, а **распаковка `null` бросает `NullPointerException`**.

## Why wrapper types exist

Примитив нельзя положить в коллекцию или подставить как аргумент типа — дженерики и коллекции работают только со ссылочными типами. Обёртки закрывают этот разрыв: `List<Integer>`, `Map<String, Double>`, `Optional<Long>` — и заодно дают `null` как «значение не задано», которого у примитива нет. У каждого из восьми примитивов ровно одна обёртка. Автоупаковка избавляет от ручных `Integer.valueOf`/`intValue`, вставляя их за вас в подходящем контексте.

## Where it happens implicitly

В подходящем контексте (присваивание, вызов метода, числовой контекст) компилятор вставляет упаковку и распаковку сам. Явные формы — `Integer.valueOf(int)` для упаковки и `intValue()`/`doubleValue()`/… для распаковки — обычно не нужны, но существуют.

```java
Integer boxed = 10;         // boxing: int 10 → Integer (== Integer.valueOf(10))
int back = boxed;           // unboxing: Integer → int (== boxed.intValue())

List<Integer> xs = new ArrayList<>();
xs.add(5);                  // boxing: int → Integer при передаче аргумента
int first = xs.get(0);      // unboxing: Integer → int при присваивании
```

## The cost: allocation is possible, not guaranteed

Упаковка **может** создать объект — но не обязана: для значений в кэш-диапазоне (см. ниже) обёртка берётся из кэша, а не аллоцируется, а JIT в состоянии и вовсе убрать упаковку (scalar replacement) там, где объект не «убегает». Поэтому «каждая упаковка = аллокация» — упрощение. Тем не менее в горячем цикле неявная упаковка нового значения незаметно порождает объекты и нагружает сборщик мусора; типичная причина — обёртка в роли аккумулятора.

```java
Long sum = 0L;                       // обёртка вместо примитива!
for (long i = 0; i < 1_000_000; i++) {
    sum += i;                        // каждая итерация: unbox → сложение → box (обычно новый Long)
}
```
Правильно: считать в примитиве (`long sum = 0L`), обёртку брать только там, где действительно нужен объект. Формально упаковка может даже бросить `OutOfMemoryError` (JLS §5.1.7), если новую обёртку нужно аллоцировать, а памяти нет.

## Unboxing null throws

Обёртка — ссылочный тип, её значением может быть `null`. Распаковка `null` — это попытка вызвать метод (`intValue()`) на `null`-ссылке, а значит `NullPointerException`, причём в местах, где его не ждёшь: в арифметике, в условии, в `switch`, при возврате из метода.

```java
Integer count = null;
int n = count;              // NullPointerException: распаковка null

Map<String, Integer> m = new HashMap<>();
int total = m.get("missing"); // get вернул null → unboxing → NullPointerException
```

Особенно коварен тернарный оператор: если одна ветка примитивная, а другая — обёртка, тип всего выражения становится примитивным, и выбранная ветка-обёртка распаковывается — NPE прилетает даже при `Integer`-цели, если выбрана `null`-ветка (см. [[5.13 Common Mistakes and Pitfalls]]). Ради этого случая JLS даже определяет упаковку **на null-типе** (null → null): условный оператор применяет boxing к типам своих ветвей, и правило нужно для полноты.

## Permitted chains

В одном шаге присваивания или вызова упаковка/распаковка комбинируется с другими родами только по фиксированным шаблонам (§5.2, §5.3):

- `boxing` — `int` → `Integer`;
- `boxing` → widening reference — `int` → `Integer` → `Object`;
- `unboxing` — `Integer` → `int`;
- `unboxing` → widening primitive — `Integer` → `int` → `long`;
- widening reference → `unboxing` (→ widening primitive) — формально в списке, но для финальных обёрток практически недостижимо (у них нет собственных подтипов); реально такое звено возникает лишь в casting-контексте как narrowing reference → unboxing (`(int) obj`, см. [[5.11 Casting Contexts]]).

```java
Object o = 5;               // boxing → widening reference
Integer i = 5;
long sum = i + 1L;          // unboxing → widening primitive (числовой контекст)
```

Чего в этом списке **нет** — «расширение примитива + упаковка» за один шаг:

```java
Long x = 8;                 // DOES NOT COMPILE: нужно int→long (widening) И →Long (boxing) сразу
Long a = 8L;                // ок: литерал уже long → одна упаковка
Long c = Long.valueOf(8);   // ок: valueOf(long) — int-аргумент сам расширится
```

Единственное исключение — сужение целочисленной **константы** с упаковкой: `Byte b = 12;` компилируется (значение известно и влезает), но лишь для константы и лишь при присваивании ([[5.9 Assignment Contexts]]).

## Wrapper identity: the exact guarantee and its boundary

Упаковка даёт **объект**, поэтому `==` между обёртками сравнивает ссылки, а не числа. JLS §5.1.7 даёт **точную** гарантию тождества: если упаковывается **константное выражение** типа `boolean`/`byte`/`char`/`short`/`int`/`long`, и значение — `true`/`false`, символ U+0000…U+007F или целое `−128`…`127`, то любые две упаковки дают `==`-идентичные ссылки. Вне этих значений (и для `Float`/`Double` всегда) тождество **не гарантируется** — реализация вольна создать новый объект.

| Обёртка | Гарантированный `==`-диапазон |
|---|---|
| `Boolean` | `true`, `false` |
| `Byte` | все значения (−128…127) |
| `Character` | U+0000…U+007F (0…127) |
| `Short`, `Integer`, `Long` | −128…127 |
| `Float`, `Double` | никогда не гарантирован |

```java
Integer p = 100, q = 100;
System.out.println(p == q);      // true  — в кэш-диапазоне
Integer r = 1000, s = 1000;
System.out.println(r == s);      // false — вне диапазона, гарантии нет
System.out.println(r.equals(s)); // true  — сравнение по значению
Double d1 = 1.0, d2 = 1.0;
System.out.println(d1 == d2);    // false — Double не кэшируется
```

Практический вывод один и жёсткий: **никогда не сравнивать обёртки через `==`** — только `equals` или распаковка. Полный разбор кэша и контракта `equals` — Ch. 49.

Но стоит одному операнду стать **примитивным**, как включается числовой контекст: обёртка распаковывается, и `==` сравнивает значения, а не ссылки — противоположно паре обёрток.

```java
Integer big = 1000;
int prim = 1000;
System.out.println(big == prim); // true — big распаковывается, сравнение по значению
```

## Common Mistakes

- Распаковывать значение, которое может быть `null` (результат `Map.get`, поле-обёртка, ответ БД).

```java
Integer score = user.getScore(); // может быть null
int doubled = score * 2;          // NullPointerException, если score == null
```
  Правильно: проверять `null` или значение по умолчанию — `int s = score != null ? score : 0;`.

- Ждать, что `int` сам доедет до `Long`/`Double`-обёртки.

```java
Double d = 5;               // DOES NOT COMPILE: int→double→Double за один шаг нельзя
```
  Правильно: `Double d = 5.0;` или `Double.valueOf(5)`.

- Сравнивать обёртки через `==`, полагаясь на кэш.

```java
Integer a = 1000, b = 1000;
if (a == b) { }             // false — вне гарантированного диапазона
```
  Правильно: `a.equals(b)` или сравнивать распакованные примитивы.

- Использовать обёртку-аккумулятор в цикле.

```java
Integer total = 0;
for (int i = 0; i < 1_000_000; i++) total += i; // лишние Integer через unbox/box
```
  Правильно: примитив `int total`.
