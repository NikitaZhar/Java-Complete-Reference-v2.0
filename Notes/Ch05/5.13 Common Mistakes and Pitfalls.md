# 5.13 Common Mistakes and Pitfalls

Сводный диагностический блок ошибок уровня главы. Почти все они растут из одного корня — из **невидимости преобразований**: компилятор и JVM вставляют их молча, а результат либо теряет данные без предупреждения, либо падает там, где перехода «не было видно». Ниже — сначала ловушки самих преобразований (дом — эта глава), затем смежные темы, чей дом в других главах (коротко, со ссылкой). Формат: проблема → код → как правильно.

## Ловушки самих преобразований

Молчаливое переполнение при сужении. Каст в узкий тип не клампит, а берёт младшие биты; данные теряются без исключения.

```java
long v = 3_000_000_000L;
int n = (int) v;            // молча → -1294967296
```
Правильно: `Math.toIntExact(v)` — бросит `ArithmeticException` ([[5.3 Narrowing Primitive Conversion]]).

Неявное сужение работает только для **константы** и только в присваивании. Ни переменная (даже в диапазоне), ни вызов метода его не получают.

```java
int code = 65;
char c = code;              // DOES NOT COMPILE: code — переменная, не константа
void ship(short s) {}
ship(100);                  // DOES NOT COMPILE: invocation не сужает даже константу
```
Правильно: `final int code = 65;` либо каст `(char) code`; в вызове — `ship((short) 100)` ([[5.9 Assignment Contexts]], [[5.10 Invocation Contexts]]).

Потеря точности при расширении в `float`/`double`. Расширение не переполняется, но огрубляет большие целые.

```java
long id = 9_007_199_254_740_993L;
double d = id;
System.out.println((long) d == id); // false — младший бит потерян
```
Правильно: не гонять точные большие целые через `double` ([[5.2 Identity and Widening Primitive Conversion]]).

Распаковка `null` роняет в неожиданных местах — в арифметике, условии, `switch`, `return`.

```java
Map<String, Integer> m = new HashMap<>();
int total = m.get("absent"); // get вернул null → unboxing → NullPointerException
```
Правильно: `m.getOrDefault("absent", 0)` или проверка на `null` ([[5.4 Boxing and Unboxing Conversion]]).

Тернар/`switch`, смешивающий обёртку и примитив, делает тип выражения примитивным и распаковывает выбранную ветку. Если она `null` — NPE даже при `Integer`-цели.

```java
Integer count = null;
Integer result = true ? count : 0; // тип выражения — int из-за ветки 0;
                                   // count распаковывается → NullPointerException
```
Правильно: не смешивать обёртку и примитив в ветках — обе обёрткой (`true ? count : Integer.valueOf(0)`) или обработать `null` заранее.

Упаковка не комбинируется с расширением примитива за один шаг.

```java
Long id2 = 8;               // DOES NOT COMPILE: int→long→Long за раз нельзя
```
Правильно: `Long id2 = 8L;` или `Long.valueOf(8)` ([[5.4 Boxing and Unboxing Conversion]]).

Каст с **примитивной целью** не всегда безопасен: `(int) obj` — это цепочка «сужение ссылки → распаковка» и может бросить `ClassCastException`/`NullPointerException`.

```java
Object o = "x";
int j = (int) o;            // ClassCastException, а не тихое сужение
```
Правильно: сперва `instanceof`-проверка ([[5.11 Casting Contexts]], [[5.14 Testing Contexts and Pattern Compatibility]]).

`(List<String>) obj` проверяется только частично. JVM проверяет, что это `List`, но не тип элементов — несовместимый элемент всплывёт позже как `ClassCastException` вдали от места каста (heap pollution).

Правильно: избегать unchecked-каста; если неизбежен — `@SuppressWarnings("unchecked")` как осознанное принятие ответственности ([[5.5 Widening and Narrowing Reference Conversion]]).

Условный/`switch` без узкого соседа не сужает константу. `short r = flag ? 1 : 2;` не компилируется — обе ветви обычные `int`.

Правильно: узкий операнд среди ветвей или явный каст `(short)(flag ? 1 : 2)` ([[5.12 Numeric Contexts (Numeric Promotions)]]).

## NaN: сравнения ведут себя несимметрично

С `NaN` любое сравнение через `==` и отношения (`<`, `<=`, `>`, `>=`) даёт **false** — включая `NaN == NaN`; а `!=` даёт **true**. Поэтому «`x != x` истинно» — корректный тест на `NaN` наравне с `Double.isNaN`.

```java
double x = 0.0 / 0.0;       // NaN
System.out.println(x == x); // false
System.out.println(x != x); // true — корректный тест на NaN
```
Правильно: `Double.isNaN(x)` (или идиома `x != x`); `== NaN` не работает никогда. Отдельно: `Double.equals` **канонизирует** NaN (два `Double`-NaN равны через `equals`), поэтому «NaN ломает equals» — неверно; поведение обёрток и коллекций — [[4.2.7 Floating-Point Types]] и Ch. 49, а не вывод из примитивного сравнения.

## Смежные ловушки (дом в других главах)

Скрытый каст в compound assignment: `x += y` это `x = (T)(x + y)` — оператор сам вставляет сужающий каст, поэтому `i *= l;` компилируется там, где `i = i * l;` — нет, и молча теряет данные. Полная семантика составного присваивания — Ch. 15.

`double` приближён — не для денег и не для точного равенства (`0.1 + 0.2 == 0.3` → false). Для точной десятичной арифметики — `BigDecimal` (из строки: `new BigDecimal("0.1")`); свойства IEEE 754 — [[4.2.7 Floating-Point Types]].

Сравнение обёрток через `==` работает «случайно» на кэше и ломается вне его; а рядом с примитивом обёртка распаковывается и `==` сравнивает по значению — поведение зависит от типа второго операнда. Кэш, `equals`/`hashCode` — Ch. 49.

Value set conversion — **не** действующий род SE 25 (удалён с Java 17); встретив его в старом источнике, игнорируйте ([[5.1 Kinds of Conversion — Overview]]).
