# 5.8 Conversion Contexts — Overview

Роды преобразований из Part A сами по себе не отвечают на вопрос «скомпилируется ли этот код» — ответ даёт **контекст**: синтаксическое место, где стоит выражение. Каждый контекст разрешает применять неявно **своё подмножество** родов, и подмножества эти разные: присваивание допускает одно, вызов метода — чуть меньше, каст — почти всё. Этот раздел сводит пять практически важных контекстов в одну карту, чтобы дальше (5.9–5.12) разбирать каждый предметно. Главная мысль: правило «род × контекст» — не бюрократия, а то, из-за чего `byte b = 100;` компилируется, а `foo(100)` для `foo(byte)` — нет.

## The five contexts

Присваивание (assignment) — правая часть `=` приводится к типу переменной; сюда же инициализация полей, `return`, элементы инициализатора массива. Вызов метода (invocation) — каждый аргумент приводится к типу параметра. Каст (casting) — оператор `(Type)` применяет преобразование явно. Конкатенация строк (string) — операнд `+` при строке рядом. Числовой (numeric) — операнды арифметических, сравнивающих и подобных операторов проходят числовое продвижение.

## Which kinds each context allows

Таблица показывает, какие роды преобразований контекст применяет **неявно** (без каста). Пустая клетка не значит «невозможно вообще» — часто это возможно через явный каст (то есть в casting-контексте).

| Род \ Контекст | Assignment | Invocation | Casting | Numeric |
|---|---|---|---|---|
| Identity | да | да | да | да |
| Widening primitive | да | да | да | да |
| Narrowing primitive | только для константы (в т. ч. с упаковкой) | нет | да (явно) | нет |
| Boxing | да | да | да | нет |
| Unboxing | да | да | да | да |
| Widening reference | да | да | да | — |
| Narrowing reference | нет | нет | да (явно) | — |
| String | — | — | — | — |
| Unchecked | да (с warning) | да (с warning) | да (с warning) | — |

Три вывода читаются прямо из таблицы. Во-первых, **casting-контекст — самый широкий**: он разрешает и сужения примитивов, и сужения ссылок, которых нет в присваивании и вызове. Во-вторых, **assignment щедрее invocation ровно в одном месте** — сужение константного целочисленного выражения: `byte b = 100;` в присваивании легально, а тот же `100` при вызове `foo(byte)` уже требует каста. В-третьих, **числовой контекст не упаковывает**: он распаковывает обёртки и расширяет примитивы, но обратно в обёртки ничего не заворачивает — арифметика идёт над примитивами.

```java
int i = 100;
byte b1 = 100;          // assignment: narrowing КОНСТАНТЫ 100 → byte, ок без каста
byte b2 = i;            // assignment: narrowing переменной запрещён → DOES NOT COMPILE
byte b3 = (byte) i;     // casting: narrowing разрешён явно
Integer boxed = i;      // assignment: boxing, ок
long sum = boxed + 1;   // numeric: unboxing Integer→int, затем widening — но НЕ boxing обратно
```

## How contexts compose conversions

Внутри одного контекста может примениться **цепочка** из нескольких родов, но по строго заданным шаблонам. Например, распаковка допускает последующее расширение примитива (`Integer`→`int`→`long`), а упаковка — последующее расширение ссылки (`int`→`Integer`→`Object`). Но «расширение примитива + упаковка» за один шаг запрещено во всех контекстах — отсюда невозможность `Long x = 8;` (разбор — [[5.4 Boxing and Unboxing Conversion]]). При этом есть обратная асимметрия: **сужение** целочисленной константы с упаковкой (`Byte b = 12;`) в присваивании разрешено — единственный случай, когда упаковка комбинируется с числовым преобразованием (см. [[5.9 Assignment Contexts]]). Эти шаблоны и отличают контексты друг от друга; детально — в разделах ниже.

## Common Mistakes

- Переносить интуицию присваивания на вызов метода для константного сужения.

```java
void ship(short s) {}
short ok = 100;         // assignment: ок
ship(100);              // DOES NOT COMPILE: invocation не сужает даже константу
```
  Правильно: `ship((short) 100);` — явный каст в вызове.

- Ждать, что числовой контекст вернёт обёртку.

```java
Integer a = 5, b = 7;
Integer c = a + b;      // компилируется: a,b распакованы, сложены как int, результат УПАКОВАН при присваивании
```
  Здесь упаковка происходит уже в assignment-контексте (`Integer c = <int>`), а не в числовом; понимать, где именно род применяется, — ключ к предсказуемости.
