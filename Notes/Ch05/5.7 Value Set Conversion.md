# 5.7 Value Set Conversion

Преобразование множеств значений (value set conversion) — самый узкоспециальный род: оно не меняет тип и почти никогда не пишется явно, но формально применяется к каждому промежуточному результату вычислений с плавающей точкой. Исторически JVM разрешала хранить `float`/`double` в регистрах повышенной точности (extended-exponent value sets), и value set conversion описывало момент, когда такое расширенное значение приводится к «настоящему» 32- или 64-битному представлению. Этот раздел объясняет, зачем род вообще существует и почему на современной Java он практически перестал влиять на результат — ключевое слово `strictfp` стало бессмысленным начиная с Java 17.

## The two value sets

JLS для `float` и `double` определяет по два множества значений: стандартное (ровно то, что описывает IEEE 754 для 32/64 бит) и расширенное по экспоненте (то же число значащих бит мантиссы, но более широкий диапазон экспоненты — как в 80-битных регистрах x87). Value set conversion — это отображение значения из расширенного множества в стандартное. Оно может дать другой результат только там, где промежуточное вычисление хранилось с расширенной экспонентой и затем «схлопывалось»; для самих битовых представлений `float`/`double` в памяти множество всегда стандартное.

## strictfp and why it no longer matters

До Java 17 поведением управляло ключевое слово `strictfp`: помеченный им класс или метод обязан был использовать только стандартные множества значений, гарантируя побитово одинаковый результат вычислений на любой платформе; без него JVM могла пользоваться расширенной точностью и давать чуть разные результаты на разном железе.

Начиная с Java 17 (JEP 306, «Restore Always-Strict Floating-Point Semantics») вся арифметика с плавающей точкой снова **всегда строгая**: расширенные множества больше не используются, результат детерминирован независимо от платформы. Поэтому `strictfp` стал избыточным — он ничего не меняет и сохранён лишь для обратной совместимости; ставить его в новом коде не нужно.

```java
// До Java 17 это могло влиять на воспроизводимость результата на разных платформах:
strictfp double compute(double a, double b) { return a * b + 1.0; }

// Начиная с Java 17 арифметика всегда строгая, и модификатор ничего не добавляет:
double compute2(double a, double b) { return a * b + 1.0; } // тот же результат везде
```

Практический вывод: на Java 17+ о value set conversion можно не думать — вычисления `float`/`double` уже воспроизводимы. Свойства самих вещественных типов (IEEE 754, `NaN`, `Infinity`, потеря точности) — дом [[4.2 Primitive Types and Values]] и раздел ошибок [[5.13 Common Mistakes and Pitfalls]]; здесь важен лишь статус рода и снятие вопроса о `strictfp`.

## Common Mistakes

- Ставить `strictfp` в новом коде, считая, что он «повышает точность» вычислений.

```java
strictfp class Calc { }     // на Java 17+ не даёт ничего: строгость и так всегда включена
```
  Правильно: не использовать `strictfp` в коде для Java 17+; на воспроизводимость он больше не влияет.

- Путать «строгую семантику» с «отсутствием ошибок округления»: детерминированность результата не отменяет приближённость `double` (`0.1 + 0.2 != 0.3`). Правильно: для точных дробных величин — `BigDecimal` (см. [[5.13 Common Mistakes and Pitfalls]]).
