# 5.13 Common Mistakes and Pitfalls

Сводный блок ошибок уровня главы. Почти все они растут из одного корня — из невидимости преобразований: компилятор и JVM вставляют их молча, а результат либо теряет данные без единого предупреждения, либо падает там, где перехода «не было видно». Каждая ошибка ниже дана в формате проблема → код → как правильно; детальные разборы — в соответствующих подразделах, сюда вынесены самые частые.

## Pitfalls

Молчаливое переполнение при сужении. Каст в узкий тип не клампит, а берёт младшие биты; данные теряются без исключения.

```java
long v = 3_000_000_000L;
int n = (int) v;            // молча → -1294967296
```
Правильно: `Math.toIntExact(v)` — бросит `ArithmeticException` вместо тихой порчи ([[5.3 Narrowing Primitive Conversion]]).

Скрытый каст в compound assignment. `x += y` эквивалентно `x = (T)(x + y)` — оператор сам вставляет сужающий каст, поэтому компилируется там, где явное сложение — нет, и молча теряет данные.

```java
int i = 5;
long l = 10;
i = i * l;                  // DOES NOT COMPILE: int = long
i *= l;                     // компилируется! скрытый (int) каст, при больших значениях — потеря
```
Правильно: не полагаться на скрытый каст для сужения; семантика операторов — Ch. 15.

Неявное сужение работает только для константы и только в присваивании. Ни переменная (даже в диапазоне), ни вызов метода его не получают.

```java
int code = 65;
char c = code;              // DOES NOT COMPILE: code — переменная, не константа
void ship(short s) {}
ship(100);                  // DOES NOT COMPILE: invocation не сужает даже константу
```
Правильно: `final int code = 65;` либо каст `(char) code`; в вызове — `ship((short) 100)` ([[5.9 Assignment Contexts]], [[5.10 Invocation Contexts]]).

Потеря точности при расширении в `float`/`double`. Расширение не переполняется, но огрубляет большие целые.

```java
long id = 9_007_199_254_740_993L;
double d = id;              // молча теряет младший бит
System.out.println((long) d == id); // false
```
Правильно: не гонять точные большие целые через `double`; сравнивать в целочисленном типе ([[5.2 Identity and Widening Primitive Conversion]]).

`double` приближён — не для денег и не для точного равенства.

```java
System.out.println(0.1 + 0.2 == 0.3); // false
```
Правильно: для точной десятичной арифметики — `BigDecimal` (создавать из строки: `new BigDecimal("0.1")`); свойства IEEE 754 — [[4.2 Primitive Types and Values]].

`NaN` не равен ничему, включая себя. Сравнения с `NaN` через `==`/`!=` всегда дают ложный результат.

```java
double x = 0.0 / 0.0;       // NaN
System.out.println(x == x); // false!
System.out.println(x != x); // true — единственный способ поймать NaN через ==
```
Правильно: проверять `Double.isNaN(x)`; помнить, что `NaN` ломает сортировки и `equals`-контракты на вещественных ключах.

Распаковка `null` роняет в неожиданных местах — в арифметике, условии, `switch`, `return`.

```java
Map<String, Integer> m = new HashMap<>();
int total = m.get("absent"); // get вернул null → unboxing → NullPointerException
```
Правильно: `m.getOrDefault("absent", 0)` или проверка на `null` ([[5.4 Boxing and Unboxing Conversion]]).

Смешение обёртки и примитива в тернарном операторе делает тип всего выражения примитивным. Если одна ветка — `int`, а другая — `Integer`, тип условного выражения становится `int`, и выбранная ветка-обёртка распаковывается — даже когда цель объявлена как `Integer`. Держит выбранная ветка `null` — получаем NPE там, где по типам его не ждёшь.

```java
Integer count = null;
Integer result = true ? count : 0; // тип выражения — int из-за ветки 0; count
                                   // распаковывается → NullPointerException,
                                   // хотя и count, и result имеют тип Integer
```
Правильно: не смешивать обёртку и примитив в ветках — сделать обе обёрткой (`true ? count : Integer.valueOf(0)`) или обработать `null` заранее. Невыбранная ветка не вычисляется, поэтому опасна именно выбранная `null`-ветка.

Упаковка не комбинируется с расширением. `int`-значение не доедет до широкой обёртки за один шаг.

```java
Long id = 8;                // DOES NOT COMPILE: int→long→Long за раз нельзя
```
Правильно: `Long id = 8L;` или `Long.valueOf(8)` ([[5.4 Boxing and Unboxing Conversion]]).

Обёртки в `switch` и дженериках. `switch` по обёртке (`Integer`) неявно распаковывает селектор — `null` даёт NPE (кроме `case null` начиная с Java 21). В дженериках всё параметризуется обёртками (`List<Integer>`), и каждый `add`/`get` — скрытая упаковка/распаковка, что и стоимость, и риск NPE.

```java
Integer sel = null;
switch (sel) {              // NPE при распаковке null (без case null)
    case 1 -> {}
    default -> {}
}
```
Правильно: обрабатывать `null` до `switch` или добавить `case null` (Java 21+); в дженериках-«числодробилках» рассматривать примитивные специализации (`IntStream`, массивы) там, где важна производительность.

Сравнение обёрток через `==`. Работает «случайно» на кэше −128..127 и ломается вне его. И зеркальная тонкость: если один операнд примитивный, обёртка распаковывается и `==` сравнивает уже по значению — то есть поведение `==` зависит от типа второго операнда.

```java
Integer a = 1000, b = 1000;
System.out.println(a == b); // false — обёртка==обёртка: сравнение ссылок
int c = 1000;
System.out.println(a == c); // true  — обёртка==примитив: a распаковывается, сравнение по значению
```
Правильно: `a.equals(b)` или сравнивать распакованные примитивы; кэш и контракт `equals` — Ch. 49.
