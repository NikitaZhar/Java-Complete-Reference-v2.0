# 4.2.7 Floating-Point Types

Вещественных типов два: `float` (32 бита) и `double` (64 бита), оба по стандарту IEEE 754. Это точка, где интуиция «числа как в математике» перестаёт работать: вещественные значения приближённы, у них есть `NaN` и бесконечности, а привычные операции ведут себя иначе, чем у целых. Здесь собрана механика, общая для обоих типов; специфика и выбор между ними — [[4.2.8 float]] и [[4.2.9 double]].

## Why decimals are not exact

IEEE 754 хранит число как двоичную дробь: знак, показатель степени двойки и мантисса. Многие привычные десятичные дроби в двоичной системе периодичны и в конечное число бит не укладываются — ровно как `1/3` не записать конечной десятичной дробью. Поэтому `0.1`, `0.2`, `0.3` хранятся приближённо, и арифметика над ними накапливает погрешность.

```java
System.out.println(0.1 + 0.2);          // 0.30000000000000004, а не 0.3
System.out.println(0.1 + 0.2 == 0.3);   // false
```

Это не баг Java и не ошибка процессора — это фундаментальное свойство двоичного представления, одинаковое во всех языках с IEEE 754. Практический вывод один: **вещественные типы нельзя использовать для денег и любых точных десятичных расчётов**. Для денег берут целые в минимальных единицах (копейки, центы) или `BigDecimal` с явным масштабом и округлением — его дом Ch. 49/50, сюда вынесен ссылкой.

## Never compare with ==

Из приближённости следует, что сравнивать вещественные на точное равенство `==` почти всегда неправильно: два «равных по смыслу» результата отличаются в младших битах. Сравнивают по модулю разности с малым порогом (эпсилон), подобранным под задачу.

```java
double a = 0.1 + 0.2, b = 0.3;
boolean eq = Math.abs(a - b) < 1e-9;    // так — правильно
```

## NaN and infinities: floating-point does not throw

У вещественных типов есть значения, которых нет у целых, и это меняет поведение при «недопустимых» операциях. Деление на ноль у целых бросает `ArithmeticException` — а у вещественных **не бросает ничего**, возвращая специальное значение:

```java
System.out.println(1.0 / 0.0);   // Infinity
System.out.println(-1.0 / 0.0);  // -Infinity
System.out.println(0.0 / 0.0);   // NaN (не число)
```

`NaN` — «не число» (Not a Number) — результат неопределённых операций (`0.0/0.0`, `Math.sqrt(-1)`). У него есть противоречивое, но важное свойство: **`NaN` не равен ничему, включая самого себя**.

```java
double nan = 0.0 / 0.0;
System.out.println(nan == nan);        // false! — единственное значение, не равное себе
System.out.println(Double.isNaN(nan)); // true — правильный способ проверки
```

Отсюда практическое правило: проверять на `NaN` только через `Double.isNaN`/`Float.isNaN`, а не через `== NaN` (что всегда ложно). Есть и ещё одна тонкость представления — знаковый ноль: `0.0` и `-0.0` различны в битах и, например, `1.0/0.0` даёт `+Infinity`, а `1.0/-0.0` — `-Infinity`, хотя `0.0 == -0.0` истинно.

## double is the default; float needs a suffix

Вещественный литерал без суффикса — `double`; чтобы получить `float`, нужен суффикс `f` (или `F`). `float→double` расширяется неявно, обратное сужение требует приведения и теряет точность.

```java
double d = 3.14;        // double по умолчанию
float f = 3.14f;        // f обязателен
// float bad = 3.14;    // compile-time error: double не влезает в float без приведения
double back = f;        // ок: float → double, расширение
```

Значения по умолчанию — `0.0` и `0.0f` ([[4.2.14 Default Values and Initialization]]). Обёртки — `Float` и `Double` ([[4.2.13 Boxing and Unboxing]]).

## Common Mistakes

- Хранить деньги в `double`.

```java
double price = 0.10, paid = 0.30;
double change = paid - price * 3;   // не ровно 0.0 из-за погрешности
```
  Правильно: целые копейки/центы или `BigDecimal` (Ch. 49/50).

- Сравнивать результаты через `==` (см. выше). Правильно: `Math.abs(a - b) < eps`.

- Проверять `NaN` сравнением.

```java
if (x == Double.NaN) { }   // всегда false — ветка мертва
```
  Правильно: `Double.isNaN(x)`.

- Ждать исключения при делении вещественного на ноль. Правильно: помнить про `Infinity`/`NaN` и проверять их (`Double.isInfinite`, `Double.isNaN`), иначе «заражённое» `NaN` тихо разойдётся по всем последующим вычислениям.
