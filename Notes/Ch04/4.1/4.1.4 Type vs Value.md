# 4.1.4 Type vs Value

Тип и значение легко спутать, потому что в коде они стоят рядом (`int x = 42`), но живут на разных уровнях: тип описывает допустимые значения и операции, значение — конкретное содержимое или результат вычисления. Тип может существовать без значения (`int` есть, даже если переменная не инициализирована), а значение без типа — нет. Раздел показывает, где смешение этих уровней превращается в конкретные баги; определения даны в [[4.1.1 Definition of Type]] и [[4.1.2 Definition of Value]].

Различие помогает понять проверку операций: компилятор использует статические типы, а при выполнении учитываются полученные значения и фактические классы объектов. Это не абсолютное разделение ошибок по стадиям: типы проверяются также в runtime, а значения констант могут проверяться на компиляции. Пример — допустимый downcast, который завершается `ClassCastException` ([[4.1.5 Static vs Runtime Type]]).

## The distinction in one table

|                             | Тип                                      | Значение                                       |
| --------------------------- | ---------------------------------------- | ---------------------------------------------- |
| Природа                     | абстракция (правило)                     | конкретная сущность                            |
| Роль                        | описывает допустимые значения и операции | конкретное содержимое или результат вычисления |
| Отношение                   | задаёт множество                         | элемент множества                              |
| Может быть один без другого | тип без значения — да                    | значение без типа — нет                        |

```java
int x;          // обычная локальная переменная: читать до присваивания нельзя
x = 42;         // теперь есть и значение 42 типа int
```

## Operations follow the type, not the value

Допустимость операции определяется типами операндов и правилами соответствующего контекста. Похожий внешний вид значений не делает несовместимые типы совместимыми: например, int и String нельзя сравнить через \==. При этом разные типы вообще могут быть совместимы через подтипирование или преобразование.

```java
int x = 1;
String s = "1";
boolean eq = (x == s);  // compile-time error: несравнимые типы int и String,
                        // хотя «по смыслу» значения похожи
```

Обратная сторона: одно и то же значение в разных типах ведёт себя по-разному.

```java
System.out.println(1 / 2);     // 0   — операнды int, целочисленное деление
System.out.println(1.0 / 2);   // 0.5 — один операнд double, деление вещественное
```

## Behaviour at runtime follows the value's actual type

Когда переменная ссылочного типа хранит объект подтипа, какое переопределение экземплярного метода вызовется, решает фактический тип значения, а не объявленный тип переменной. Это и есть полиморфизм; подробно — [[4.1.5 Static vs Runtime Type]].

```java
Number n = Double.valueOf(3.14);
System.out.println(n.getClass()); // class java.lang.Double
System.out.println(n);            // 3.14 — toString() берётся у Double
```

## Common Mistakes

- Делать вывод о типе по «виду» значения и ждать автоматического согласования.

```java
Object o = 42; // 42 упакован в Integer; в o хранится ссылка, статический тип o — Object
int sum = o + 1;        // compile-time error: у Object нет операции +
```
  Правильно: операции опираются на статический тип; чтобы сложить — вернуть значение к числовому типу (`(int) o + 1` после проверки, или не терять тип изначально).

- Путать «переменная имеет тип T» и «объект имеет тип T». Переменная типа `Number` может хранить `Integer`; приведение к неверному фактическому типу упадёт в runtime (см. [[4.1.5 Static vs Runtime Type]]).
