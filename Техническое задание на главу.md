## 0. Перед тем как писать: три вопроса

Прежде чем открывать редактор, ответьте письменно (2-3 строки на каждый — это не для книги, это для вас):

1. **Владелец темы.** Эта глава — первое и единственное место, где данная тема получает теорию? Или это применение уже описанного в другой части? Сверьтесь с матрицей владения темами (см. методичку из прошлого обсуждения). Если тема уже где-то раскрыта — эта глава ссылается, а не пересказывает.
2. **Аудитория и назначение части.** Part I = нормативный слой (что это и как устроено по спецификации). Part III = практика инструментов. Part IV = сертификация (можно ловушки). Part V = практика API. Part VI = продвинутое. Если пишете «типичные ошибки» — они про реальный код; если «экзаменационные ловушки» — только если это Part IV (или явно выбранный Exam Focus в Part V).
3. **Что читатель должен уметь после главы**, сформулировано как поведенческий результат («сможет отличить X от Y», «не наступит на грабли Z»), а не как «будет знать про X». Если не можете сформулировать — тема ещё не готова к написанию, нужно сузить.

## 1. Структурный скелет главы (обязательная форма)

```
### Chapter N. <Название>
N.1 <Базовое понятие/декларация>
N.2 <Следующий логический блок>
...
N.(k-1) <последний содержательный подраздел>
N.k Типичные ошибки [и best practices, если применимо]
```

- **Открывающий абзац главы** (до N.1, не пронумерован): 3-5 предложений — что это, зачем это нужно на практике, одна фраза о том, чем это НЕ является (частая причина путаницы). У Arrays это, например, чёткое разграничение массива и `Collection`-типов до того, как читатель успеет их перепутать.
- **Последний подраздел — всегда «Типичные ошибки»** (кроме Part II, где вместо этого «Практические следствия» — см. методичку). Это не опция, а часть формы главы, как и в эталоне.
- Никаких «теоретических» подразделов после «Типичных ошибок» — если что-то всплыло после, это либо отдельный подраздел до, либо повод пересмотреть структуру.

## 2. Правило одного примера на понятие

Эталонная глава не иллюстрирует одну идею тремя похожими кусками кода. На каждое новое понятие — **один** пример, который:
- Компилируется и реально отражает то, как это пишут на практике (не «нарочно скрученный» код — это признак exam-ловушки, ей тут не место, см. п.0.2);
- Показывает именно то понятие, которое обсуждается в подразделе, без побочных фич, отвлекающих внимание;
- Сопровождается 1-2 предложениями, что происходит и почему, а не построчным пересказом синтаксиса.

Если для понятия хочется дать больше одного примера — это сигнал, что понятие нужно разбить на два подраздела, либо один пример убрать в «Типичные ошибки» как контрпример.

## 3. Формат подраздела «Типичные ошибки»

Строго списком, 3–5 пунктов, каждый пункт в формате:

**Проблема (1 строка) → короткий код, который её показывает → как правильно (1 строка).**

Что запрещено в этом подразделе:
- Новая теория, которая нигде раньше не вводилась (её место — выше по главе);
- Пункты общего характера («будьте внимательны с типами») — только конкретные, воспроизводимые ошибки;
- Экзаменационные trick-примеры вне Part IV/Exam Focus (см. предыдущее обсуждение).

Ориентир по объёму: подраздел не должен быть длиннее, чем сумма всех предыдущих подразделов главы — если это так, вероятно, часть контента на самом деле теория, которая должна быть выше.

---

## 4. Перекрёстные ссылки — только по протоколу

- Ссылка на другую часть/главу — **одна строка**, без пересказа: «подробнее см. Part X, Y.Z». Пересказ сути темы, на которую ссылаетесь, — это и есть дублирование, которого мы избегаем.
- Перед тем как писать объяснение термина, проверьте глоссарий: если у термина уже есть «дом» — здесь только ссылка + одно предложение, зачем это упомянуто именно тут (мост, а не определение).
- Каждая перекрёстная ссылка в главе — с одной стороны: не создавайте циклических «см. также» без содержательной причины (это то, что произошло с 7.5/7.10 в Part II — обе стороны выглядели как равноправное определение одного и того же).

---

## 5. Терминологическая дисциплина

- Один термин — одно написание во всей книге (например, не смешивать «варианты» / «типы» для generics wildcard в разных главах).
- Термины на английском (названия классов, методов, ключевых слов) — в `коде` или *курсивом* при первом употреблении в главе, дальше просто в тексте без разметки.
- Не вводить синоним уже существующего термина ради разнообразия текста — для технической книги это создаёт ложное ощущение двух разных концепций.

## 6. Приёмочный чек-лист (заполняется по факту, до сдачи главы)

| # | Критерий | Пройдено (да/нет) |
|---|---|---|
| 1 | Есть открывающий абзац с назначением и границей темы | |
| 2 | Все подразделы пронумерованы по схеме N.1...N.k | |
| 3 | Последний подраздел — «Типичные ошибки» (или «Практические следствия» для Part II) | |
| 4 | На каждое понятие — не более одного основного примера кода | |
| 5 | Ни один пример не является надуманной exam-ловушкой (если глава не в Part IV / не Exam Focus) | |
| 6 | Все упоминания тем, уже раскрытых в других частях, — это ссылка в одну строку, без пересказа | |
| 7 | Проверено по матрице владения темами: глава не создаёт новый «дом» для уже занятой темы без явного обоснования | |
| 8 | Термины проверены по глоссарию — нет расхождений с уже использованными в других главах формулировками | |
| 9 | Подраздел «Типичные ошибки» — 3–5 пунктов в формате проблема→код→решение, без новой теории | |
| 10 | Глава читается самостоятельно (без открытых на другой вкладке трёх других глав), кроме тех мест, где явная ссылка и это осознанный выбор | |

Если хотя бы один пункт — «нет», глава не соответствует эталону и возвращается на доработку по конкретному пункту (а не «переписать всю главу»).

## 7. Как использовать этот файл на практике

- Перед написанием главы — скопировать раздел 0 и ответить на три вопроса.
- Во время написания — держать перед глазами раздел 1 (скелет) и раздел 3 (формат ошибок).
- После черновика — пройти по чек-листу раздела 6 построчно, отметить каждый пункт.
- Если пишете несколько глав подряд — раз в 3-4 главы делать выборочную сверку терминов (раздел 5) между уже написанными главами, а не полагаться на память.
