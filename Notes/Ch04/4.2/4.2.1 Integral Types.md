# 4.2.1 Integral Types

Целочисленных типов пять: `byte`, `short`, `int`, `long` и `char`. Первые четыре — знаковые в дополнительном коде (two's complement), `char` — беззнаковый 16-битный код. Здесь собрана механика, общая для всех целочисленных типов: представление, тихое переполнение, числовое продвижение (promotion) и битовые операции. Файлы отдельных типов ([[4.2.6 char]] и др.) опираются на этот раздел и не повторяют его; полные правила преобразований между типами — Ch. 5, семантика самих операторов — Ch. 15. Диапазоны и обёртки сведены в таблице [[4.2.0 Overview]].

## Two's complement: a negative is a bit pattern

Знаковые целочисленные типы хранят отрицательные числа в дополнительном коде: `-x` получается как `~x + 1`. Практический смысл — «минус» это не отдельный знак, а старший бит; арифметика и побитовые операции работают именно с битовым паттерном.

Почему именно дополнительный код, а не «знак плюс модуль»? У него два решающих достоинства. Во-первых, ноль единственный: нет отдельных `+0` и `−0`, как было бы при знаковом бите (эта аномалия останется у чисел с плавающей точкой — см. [[4.2.7 Floating-Point Types]]). Во-вторых, сложение и вычитание выполняются одной и той же аппаратной схемой независимо от знаков операндов — процессору не нужны отдельные операции для отрицательных чисел. Именно поэтому у диапазона знакового типа отрицательных значений на одно больше, чем положительных (`−128…127`): нулю не нужен второй код, и освободившийся паттерн отдан отрицательной стороне.

```java
byte b = -1;              // хранится как 1111 1111
int asUnsigned = b & 0xFF;
System.out.println(asUnsigned); // 255 — те же биты, прочитанные без знака
```

`char` знака не имеет вовсе: его диапазон 0…65 535, а `>>` и `>>>` для него дают одно и то же.

## Overflow is silent

Целочисленное переполнение в Java **не бросает исключение** — результат вычисляется по модулю 2ⁿ, и знак может внезапно смениться. Это тихий баг: логика ломается, а стектрейса нет.

Это осознанный компромисс, а не недосмотр. Проверять каждую арифметическую операцию на выход за диапазон стоило бы дополнительной инструкции и ветвления на каждый `+` и `*` — неприемлемая цена для языка, претендующего на скорость системного кода. Поэтому Java, как C и как сам процессор, молча отбрасывает старшие биты (арифметика по модулю 2ⁿ). Результат строго определён и переносим — в этом смысле поведение предсказуемо, — но ответственность за то, что число влезает в тип, лежит на программисте. Здесь и кроется противоречие, о котором стоит помнить: «предсказуемо» не значит «безопасно».

```java
int x = Integer.MAX_VALUE;   // 2 147 483 647
System.out.println(x + 1);   // -2147483648 — молча «перевернулось»
```

Когда переполнение недопустимо (счётчики денег, размеры, ID), считают через проверяемые методы `Math`:

```java
int safe = Math.addExact(x, 1);   // ArithmeticException: integer overflow
long big = (long) x + 1;          // или заранее уйти в тип пошире
```

Частный коварный случай — `Math.abs(Integer.MIN_VALUE)`: модуль минимального значения в диапазон не влезает и возвращается тем же отрицательным числом.

```java
System.out.println(Math.abs(Integer.MIN_VALUE)); // -2147483648, не положительное
```

## Numeric promotion: small integers become int

Перед арифметикой `byte`, `short` и `char` **продвигаются к `int`**, поэтому даже сумма двух `byte` имеет тип `int`. Если один операнд шире (`long`, `float`, `double`) — оба продвигаются к самому широкому.

Это удивляет новичков («складываю два байта — почему результат `int`?»), но причина не в прихоти языка, а в устройстве JVM. У виртуальной машины попросту нет арифметических инструкций для `byte` и `short`: операндный стек оперирует значениями шириной не меньше `int` (`iadd`, `imul`, `ishl` и т. д.), а для `long`, `float`, `double` есть свои наборы. Физически `byte + byte` считается как `int + int`, и язык честно присваивает результату тип `int`, а не делает вид, что это `byte`. Типы уже́ `int` — `long`, `float`, `double` — своих инструкций не теряют, поэтому не продвигаются. Отсюда классическая ошибка «результат не влезает в исходный тип»:

```java
byte a = 5, b = 10;
byte c = a + b;          // compile-time error: a + b имеет тип int
byte d = (byte) (a + b); // нужно явное сужение (с риском потери старших бит)
```

Тот же механизм делает `long`-арифметику обязательной там, где промежуточная сумма выходит за `int`:

```java
int million = 1_000_000;
long bad = million * million;        // сначала int*int переполнится, потом уйдёт в long: -727379968
long good = (long) million * million; // 1000000000000 — продвижение до умножения
```

Полные правила промоушенов и прочих преобразований — Ch. 5; здесь важно лишь следствие для целых.

## Bitwise operations and shifts

Побитовые операторы (`&`, `|`, `^`, `~`) и сдвиги (`<<`, `>>`, `>>>`) применяются к целочисленным типам; операнды меньше `int` сначала продвигаются к `int`. Разница сдвигов вправо принципиальна: `>>` тянет знаковый бит (арифметический), `>>>` дополняет нулями (логический).

```java
int n = -8;                 // 1111…1000
System.out.println(n >> 2);  // -2          — знак сохранён
System.out.println(n >>> 2); // 1073741822  — заполнение нулями
```

Типичное применение `>>>` — читать байт/число как беззнаковое; для явности вместо ручных масок лучше стандартные методы:

```java
byte raw = -1;
int u1 = raw & 0xFF;              // 255
int u2 = Byte.toUnsignedInt(raw); // 255 — читается однозначнее
```

## Common Mistakes

- Ждать исключения при переполнении.

```java
int count = Integer.MAX_VALUE;
count++;                 // -2147483648, молча
```
  Правильно: `Math.addExact`/`incrementExact` или тип пошире (`long`).

- Забыть про продвижение до умножения и переполнить `int` «внутри» long-выражения.

```java
long ms = 24 * 60 * 60 * 1000 * 1000; // int-переполнение до присваивания в long
```
  Правильно: сделать хотя бы один операнд `long` — `24L * 60 * 60 * 1000 * 1000`.

- Путать `>>` и `>>>` при обработке флагов/бинарных данных: арифметический сдвиг втащит единицы в старшие биты отрицательного числа. Правильно: для беззнаковой обработки — `>>>` или `Integer.toUnsignedLong`/`Byte.toUnsignedInt`.
