# 5.4 Boxing and Unboxing Conversion

Восемь примитивных типов и их классы-обёртки (`int`/`Integer`, `double`/`Double`, `boolean`/`Boolean` и т. д.) — два представления одних и тех же значений: одно живёт «плоско» в стеке, другое — объектом в куче. Преобразования между ними называются **упаковкой (boxing)** — примитив → обёртка — и **распаковкой (unboxing)** — обёртка → примитив; неявные их формы зовут авто-упаковкой и авто-распаковкой (autoboxing / auto-unboxing). Это дом темы: и зачем обёртки нужны, и как работает механизм упаковки, и как он ведёт себя в контекстах преобразования. Устройство самих обёрток как ссылочных типов затронуто в [[4.3 Reference Types and Values]], контракт `equals`/`hashCode` и кэш — в Ch. 49; всё остальное про boxing/unboxing — здесь. Ключевой факт, вокруг которого крутятся почти все ошибки: упаковка безопасна, а **распаковка `null` бросает `NullPointerException`**.

## Why wrapper types exist

Примитив нельзя положить в коллекцию или подставить как аргумент типа — дженерики и коллекции работают только со ссылочными типами. Обёртки закрывают этот разрыв: `List<Integer>`, `Map<String, Double>`, `Optional<Long>` — и заодно дают `null` как «значение не задано», которого у примитива нет. У каждого из восьми примитивов ровно одна обёртка: `byte`/`Byte`, `short`/`Short`, `int`/`Integer`, `long`/`Long`, `float`/`Float`, `double`/`Double`, `char`/`Character`, `boolean`/`Boolean`. Автоупаковка избавляет от ручных `Integer.valueOf`/`intValue`, вставляя их за вас в подходящем контексте.

## Where it happens implicitly

В подходящем контексте (присваивание, вызов метода, числовой контекст) компилятор вставляет упаковку и распаковку сам. Явные формы — `Integer.valueOf(int)` для упаковки и `intValue()`/`doubleValue()`/… для распаковки — обычно не нужны, но существуют.

```java
Integer boxed = 10;         // boxing: int 10 → Integer (неявно, == Integer.valueOf(10))
int back = boxed;           // unboxing: Integer → int (неявно, == boxed.intValue())

Double dRef = Double.valueOf(3.14); // явная упаковка
double d = dRef.doubleValue();      // явная распаковка

List<Integer> xs = new ArrayList<>();
xs.add(5);                  // boxing: int → Integer при передаче аргумента
int first = xs.get(0);      // unboxing: Integer → int при присваивании
```

Распаковка позволяет использовать `Boolean` там, где нужен `boolean` (в условии `if`), а обёртку целого — как операнд арифметики.

## The cost: allocation you did not ask for

Каждая упаковка — это создание объекта (или взятие его из кэша малых значений). В горячем цикле неявная упаковка незаметно порождает миллионы объектов и нагружает сборщик мусора; типичная причина — обёртка в роли аккумулятора.

```java
Long sum = 0L;                       // обёртка вместо примитива!
for (long i = 0; i < 1_000_000; i++) {
    sum += i;                        // каждая итерация: unbox → сложение → box (новый Long)
}
```
Правильно: считать в примитиве (`long sum = 0L`), обёртку брать только там, где действительно нужен объект (ключ/значение коллекции, `Optional`, `null`-семантика). На больших объёмах это разница в разы, а не микрооптимизация.

## Unboxing null throws

Обёртка — ссылочный тип, её значением может быть `null`. Распаковка `null` — это попытка вызвать метод (`intValue()`) на `null`-ссылке, а значит `NullPointerException`, причём в местах, где его не ждёшь: в арифметике, в условии, в `switch`, при возврате из метода.

```java
Integer count = null;
int n = count;              // NullPointerException: распаковка null
```

```java
Map<String, Integer> m = new HashMap<>();
int total = m.get("missing"); // get вернул null → unboxing → NullPointerException
```

Особенно коварен тернарный оператор: если одна ветка примитивная, а другая — обёртка, тип всего выражения становится примитивным, и выбранная ветка-обёртка распаковывается — NPE прилетает даже при `Integer`-цели, если выбрана `null`-ветка (см. [[5.13 Common Mistakes and Pitfalls]]).

## Boxing does not combine with other conversions

Главное правило-ловушка: в одном шаге присваивания или вызова **упаковка не комбинируется с расширением примитива**, а распаковка комбинируется с расширением только в одну сторону. Компилятор готов сделать *либо* расширение `int`→`long`, *либо* упаковку `int`→`Integer`, но не «`int`→`long`→`Long`» за один присест.

```java
Long x = 8;                 // DOES NOT COMPILE: нужно int→long (widening) И →Long (boxing) сразу
```

`8` — это `int`. Чтобы получить `Long`, потребовалось бы сначала расширить `int` до `long`, потом упаковать в `Long`; два преобразования подряд в этом контексте запрещены. Обходы:

```java
Long a = 8L;                // литерал уже long → одна упаковка long→Long
Long b = (long) 8;          // явное widening до long, потом упаковка
Long c = Long.valueOf(8);   // valueOf(long): int-аргумент сам расширится до long
```

Обратная сторона — распаковка **комбинируется** с последующим расширением примитива: `Integer`→`int`→`long` в числовом контексте работает.

```java
Integer i = 5;
long sum = i + 1L;          // i распаковывается в int, затем widening int→long — ок
```

Единственное исключение к правилу «упаковка не комбинируется» — сужение целочисленной **константы**: `Byte b = 12;` компилируется, потому что значение известно на компиляции и проверено на попадание в диапазон (сужение `int`→`byte`, затем упаковка). Но это работает лишь для константы и лишь при присваивании — разбор в [[5.9 Assignment Contexts]].

## Wrapper identity is not value

Упаковка создаёт **объект**, поэтому `==` между обёртками сравнивает ссылки, а не числа. Из-за кэша малых значений (`Integer` в диапазоне −128..127) результат `==` то `true`, то `false` в зависимости от величины — источник тонких багов. Полный разбор кэша и контракта `equals` — дом Ch. 49; здесь важно лишь помнить: содержимое обёрток сравнивают через `equals` или через распаковку в примитив.

```java
Integer p = 100, q = 100;
System.out.println(p == q);      // true  — из кэша, одна ссылка
Integer r = 1000, s = 1000;
System.out.println(r == s);      // false — разные объекты вне кэша
System.out.println(r.equals(s)); // true  — сравнение по значению
```

Но стоит одному операнду стать **примитивным**, как включается числовой контекст: обёртка распаковывается, и `==` сравнивает уже значения, а не ссылки. Поэтому `Integer` рядом с `int` ведёт себя ровно противоположно паре `Integer`–`Integer` — тут величина `1000` роли не играет.

```java
Integer big = 1000;
int prim = 1000;
System.out.println(big == prim); // true — big распаковывается, сравнение по значению
```

## Common Mistakes

- Распаковывать значение, которое может быть `null` (результат `Map.get`, поле-обёртка, ответ БД).

```java
Integer score = user.getScore(); // поле типа Integer, может быть null
int doubled = score * 2;          // NullPointerException, если score == null
```
  Правильно: проверять `null` или задавать значение по умолчанию — `int s = score != null ? score : 0;`.

- Ждать, что `int`-значение само доедет до `Long`/`Double`-обёртки.

```java
Double d = 5;               // DOES NOT COMPILE: int→double→Double за один шаг нельзя
```
  Правильно: `Double d = 5.0;` (литерал уже `double`) или `Double.valueOf(5)`.

- Сравнивать обёртки через `==`, полагаясь на кэш.

```java
Integer a = 1000, b = 1000;
if (a == b) { }             // false — не сработает вне кэша −128..127
```
  Правильно: `a.equals(b)` или сравнивать распакованные примитивы. Детали кэша — Ch. 49.

- Использовать обёртку-аккумулятор в цикле.

```java
Integer total = 0;
for (int i = 0; i < 1_000_000; i++) total += i; // миллион лишних Integer через unbox/box
```
  Правильно: примитив `int total` — обёртку брать только там, где нужен объект или `null`.
