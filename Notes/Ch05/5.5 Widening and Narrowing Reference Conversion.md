# 5.5 Widening and Narrowing Reference Conversion

У ссылочных типов «шире/уже» задаётся не диапазоном чисел, а **отношением подтипов**: тип-подтип уже своего надтипа, потому что он — специализация. Отсюда два рода ссылочных преобразований. **Расширяющее ссылочное (widening reference, upcasting)** — переход вверх по иерархии, от подтипа к надтипу (`String`→`Object`); оно всегда безопасно и неявно. **Сужающее ссылочное (narrowing reference, downcasting)** — переход вниз, от надтипа к подтипу (`Object`→`String`); оно требует явного каста и **проверяется в runtime**, а при несоответствии бросает `ClassCastException`. Механику самого отношения подтипов задаёт [[4.1.6 Subtypes and Supertypes]]; здесь — что происходит со ссылкой при переходе и почему одно направление безопасно, а другое нет.

## Upcasting: always safe, always implicit

Значение подтипа годится везде, где ожидается надтип, поэтому расширение вверх компилятор делает сам, без каста и без всякой проверки во время выполнения. Ссылка при этом не меняет объект — меняется лишь **статический тип**, через который на него смотрят; сужается набор доступных членов, но сам объект остаётся прежним (его исполняемый тип не меняется — см. [[4.1.5 Static vs Runtime Type]]).

```java
String s = "hello";
Object o = s;               // widening reference: String → Object, неявно
CharSequence cs = s;        // widening: String → интерфейс-надтип
Integer boxed = 42;
Number num = boxed;         // widening: Integer → Number
Object any = new int[]{1};  // массивы тоже подтипы Object
```

Через переменную `o` виден только API `Object`, но за ссылкой по-прежнему объект `String`; вызов переопределённого метода пойдёт по фактическому типу.

## Downcasting: explicit and runtime-checked

Обратный переход — обещание «за этой ссылкой на самом деле лежит более конкретный тип». Компилятор не может это проверить (он видит лишь статический тип надтипа), поэтому требует явного каста, а JVM в момент выполнения сверяет фактический класс объекта с целевым типом. Совпал — ссылка получает новый статический тип; не совпал — `ClassCastException`.

```java
Object o = "hello";
String s = (String) o;      // narrowing reference: проверка в runtime проходит, ок
System.out.println(s.length());

Object o2 = Integer.valueOf(7);
String bad = (String) o2;   // компилируется, но в runtime: ClassCastException
```

Чтобы downcast был безопасным, перед ним проверяют тип. Современная форма — `instanceof` с образцом (pattern), которая совмещает проверку и приведение; это конструкция Ch. 14.7, здесь она показана лишь как правильный способ избежать `ClassCastException`.

```java
Object o = fetch();
if (o instanceof String s) {   // проверка + привязка к String s
    System.out.println(s.length());
}
```

## What the compiler rejects outright

Каст между ссылочными типами, у которых **нет** отношения подтипа ни в одну сторону и которые не связаны через интерфейс, компилятор отвергает сразу — до всякого runtime. Между несвязанными классами преобразования не существует.

```java
String s = "x";
Integer i = (Integer) s;    // DOES NOT COMPILE: inconvertible types, String и Integer несвязаны
```

Литерал `null` — особый случай: он приводится к любому ссылочному типу и проходит любой downcast без исключения, потому что проверять нечего.

```java
Object o = null;
String s = (String) o;      // ок: null кастуется к любому ссылочному типу, без CCE
```

## Generics: unchecked and capture — здесь только ссылка

С дженериками связаны ещё два рода ссылочных преобразований: **unchecked** (между «сырым» `List` и `List<String>`, с предупреждением компилятора) и **capture** (захват wildcard `List<?>`). Из-за стирания типов они проверяются лишь частично и могут привести к `ClassCastException` «на ровном месте» (heap pollution). Их полное раскрытие — дом Ch. 20; здесь достаточно знать, что они существуют и почему `@SuppressWarnings("unchecked")` — это принятие на себя ответственности за необеспеченную типобезопасность.

## Common Mistakes

- Делать downcast без проверки типа.

```java
Object o = config.get("port");
Integer port = (Integer) o;     // ClassCastException, если там оказалась String
```
  Правильно: `if (o instanceof Integer port) { … }` — проверить перед использованием.

- Путать смену статического типа со сменой объекта: upcast не «превращает» объект и не теряет переопределённое поведение.

```java
Object o = new ArrayList<String>();
o.add("x");                     // DOES NOT COMPILE: у Object нет add — виден только API Object
```
  Правильно: обращаться через подходящий статический тип (`List<String> list = …; list.add("x");`).

- Кастовать между несвязанными типами, надеясь на runtime.

```java
Number n = 5;
String s = (String) n;          // DOES NOT COMPILE: Number и String несовместимы
```
  Правильно: преобразовывать значением, а не кастом — `String s = n.toString();`.
