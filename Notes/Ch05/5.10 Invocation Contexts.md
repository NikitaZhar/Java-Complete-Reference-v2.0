# 5.10 Invocation Contexts

Контекст вызова (invocation context) возникает при передаче аргументов в метод или конструктор: значение каждого аргумента приводится к типу соответствующего формального параметра. Набор разрешённых преобразований почти совпадает с присваиванием — расширение примитива, упаковка/распаковка, расширение ссылки, unchecked, — но с одним принципиальным отличием: **в вызове нет исключения для сужения константы**. То, что в присваивании проходит (`byte b = 100;`), при передаче в метод `f(byte)` уже требует каста. Кроме того, именно в этом контексте живёт **разрешение перегрузки**; полная его теория (выбор наиболее специфичного метода) — дом главы о методах (Ch. 8.4.4), здесь — слой преобразований: какие переходы аргументов допускает каждый режим вызова.

## Strict, loose, and variable-arity: three invocation modes

JLS (§5.3, §15.12.2) определяет вызов как **три режима-контекста**, применяемых по очереди; компилятор берёт первый, в котором находится применимый метод:

- **Strict invocation** (фаза 1) — только тождество, расширение примитива и расширение ссылки. Ни упаковки/распаковки, ни varargs.
- **Loose invocation** (фаза 2) — добавляются упаковка, распаковка и unchecked. Всё ещё без varargs.
- **Variable-arity invocation** (фаза 3) — то же, что loose, плюс varargs (`T...`).

Порядок фаз задаёт приоритеты: «более точное» примитивное расширение (strict) выигрывает у упаковки (loose), а фиксированная арность — у varargs.

```java
static void m(long x)    { System.out.println("long"); }
static void m(Integer x) { System.out.println("Integer"); }

m(5);   // "long": strict-фаза (widening int→long) находит метод раньше,
        // чем loose-фаза (boxing int→Integer)
```

Практический пример из книг: какой метод выбран — зависит от того, какое преобразование аргумента возможно и в какой фазе.

```java
static void climb(long t)    {}   // int пройдёт widening (strict)
static void swing(Integer u) {}   // int пройдёт boxing (loose)

climb(123);   // widening int→long (strict)
swing(123);   // boxing int→Integer (loose)
// jump(123L) к jump(int) — DOES NOT COMPILE: long→int это сужение, ни в одной фазе неявно нет
```

## Invocation differs from assignment: no constant narrowing

Единственная содержательная разница с присваиванием: инвокация **не** выполняет неявное сужение константного целочисленного выражения — ни в strict, ни в loose. Диапазон значения роли не играет: важно, что это вызов.

```java
void ship(short qty) {}
short s = 100;          // assignment: константное сужение int→short, ок
// ship(100);           // DOES NOT COMPILE: invocation не сужает даже константу 100
ship((short) 100);      // ок: явный каст
```

То же с упаковкой: сокращение «сужение константы + упаковка», разрешённое в присваивании (`Character c = 32;`), в вызове не действует — `Character.valueOf(32)` не компилируется (сигнатура `valueOf(char)`, а `32` — `int`).

## Boxing plus widening does not combine here either

Правило «упаковка не комбинируется с расширением примитива» (см. [[5.4 Boxing and Unboxing Conversion]]) действует и в вызове: аргумент `int` не доедет до параметра `Long` сам.

```java
static void rest(Long x) {}
// rest(8);        // DOES NOT COMPILE: нужно int→long И →Long за раз — нельзя
rest(8L);          // ок: long-литерал → одна упаковка Long
```

## Ambiguous calls

Когда два метода применимы, но ни один не является **наиболее специфичным**, вызов **неоднозначен** — ошибка компиляции. Классический случай (Mughal, Example 5.3): разные параметры требуют упаковки в разные стороны, и ни одна сигнатура не «уже» другой.

```java
static void callMe(long x, Integer y) {}   // (1)
static void callMe(Integer x, long y) {}   // (2)

// callMe(20, 17);                 // DOES NOT COMPILE: reference to callMe is ambiguous —
//                                 //   для (1) нужно упаковать 2-й аргумент, для (2) — 1-й
callMe(20, Integer.valueOf(17));   // ок: явный тип снимает неоднозначность → (1)
```

Снять неоднозначность можно, сделав типы аргументов конкретнее (явный каст или обёртка) — тогда одна из сигнатур становится точно применимой без «симметричной» упаковки.

## Unchecked invocation with raw arguments

Как и присваивание, вызов допускает **unchecked**-преобразование — передачу «сырого» типа туда, где ждут параметризованный, — с предупреждением: типобезопасность не гарантируется.

```java
static void take(List<String> ls) {}
List raw = new ArrayList();
take(raw);         // unchecked method invocation warning — компилируется, но небезопасно
```

## Constructors and generic methods

Всё сказанное относится и к **конструкторам**: `new StringBuilder(16)` разрешается тем же перебором перегрузок и теми же преобразованиями аргументов. Для **обобщённых методов** сначала выводятся аргументы типа (type inference, дом Ch. 20), а уже к выведенной сигнатуре применяются invocation-преобразования.

```java
StringBuilder sb = new StringBuilder(16);     // конструктор: перегрузка (int) capacity
static <T> T firstOf(List<T> xs) { return xs.get(0); }
String first = firstOf(List.of("x"));         // выведен T=String, затем invocation
```

## Varargs as the last resort

Метод с переменным числом аргументов применяется только в третьей фазе — после фиксированной арности. Поэтому при наличии точного не-varargs метода varargs проигрывает.

```java
static void f(int a, int b)   { System.out.println("pair"); }
static void f(int... nums)    { System.out.println("varargs"); }

f(1, 2);        // "pair": фиксированная арность (фазы 1/2) раньше varargs (фаза 3)
f(1, 2, 3);     // "varargs": пары нет, подходит только версия с varargs
```

## Common Mistakes

- Переносить константное сужение из присваивания в вызов.

```java
void setAge(byte age) {}
// setAge(30);          // DOES NOT COMPILE, хотя byte age = 30; было бы легально
setAge((byte) 30);      // правильно
```

- Ждать, что перегрузка выберет упакованный вариант, когда возможно расширение: при `m(long)` и `m(Integer)` вызов `m(5)` уйдёт в `m(long)` (strict раньше loose). Нужен `Integer` — передать `Integer.valueOf(5)`.

- Рассчитывать, что `int`-аргумент подойдёт к параметру-обёртке шире своего типа (`Long`, `Double`): `rest(8)` к `rest(Long)` не компилируется — нужен `rest(8L)`.

- Оставлять неоднозначный вызов «на авось»: если обе перегрузки требуют симметричной упаковки, компилятор откажет — уточняйте тип аргумента.
