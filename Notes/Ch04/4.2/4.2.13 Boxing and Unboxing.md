# 4.2.13 Boxing and Unboxing

У каждого примитива есть объектная обёртка (`int`↔`Integer`, `double`↔`Double`, `boolean`↔`Boolean` и т. д.). Автоупаковка (autoboxing) — неявное превращение примитива в обёртку, распаковка (unboxing) — обратное. Механизм удобен и почти невидим, и именно поэтому порождает ошибки: аллокации там, где их не ждёшь, и `NullPointerException` на пустом месте. Здесь — дом механики упаковки; кэш обёрток и связанная с ним ловушка `==` вынесены в Ch. 49 и [[4.1.8 Common Pitfalls]].

## Why wrappers exist and where boxing happens

Примитив нельзя положить в коллекцию или generic-тип — они работают только со ссылочными типами (см. [[4.1.3 High-Level Classification of Types]]). Обёртки закрывают этот разрыв: `List<Integer>`, `Map<String, Double>`, а заодно дают `null` как «значение не задано». Автоупаковка избавляет от ручных `Integer.valueOf`/`intValue`, вставляя их за вас — при присваивании, передаче аргументов, в коллекциях, в арифметике над обёртками.

```java
Integer boxed = 42;          // autoboxing: Integer.valueOf(42)
int back = boxed;            // unboxing: boxed.intValue()
List<Integer> xs = new ArrayList<>();
xs.add(7);                   // autoboxing при добавлении
int first = xs.get(0);       // unboxing при чтении
```

## The cost: allocation you did not ask for

Каждая упаковка — это создание (или взятие из кэша) объекта. В горячем цикле неявная упаковка незаметно порождает миллионы объектов и нагружает сборщик мусора:

```java
Long sum = 0L;                       // обёртка!
for (long i = 0; i < 1_000_000; i++) {
    sum += i;                        // на каждой итерации: unbox → сложение → box (новый Long)
}
```
Правильно: считать в примитиве (`long sum = 0L`), обёртку брать только там, где нужен объект. Это не микрооптимизация, а разница в разы на больших объёмах.

## The trap: unboxing null throws

Обёртка допускает `null`, а распаковка `null` невозможна — попытка даёт `NullPointerException`, часто в неожиданном месте, потому что распаковка неявна.

```java
Map<String, Integer> counts = new HashMap<>();
int n = counts.get("missing");   // get вернул null → unboxing → NullPointerException
```

Особенно коварен тернарный оператор: если его ветви смешивают обёртку и примитив, весь результат распаковывается, и `null`-ветка роняет программу, даже когда «не выбрана» по значению.

```java
Integer boxed = null;
boolean flag = true;
int v = flag ? 1 : boxed;   // тип выражения — int, обе ветви распаковываются →
                            // NullPointerException, хотя boxed «не выбран»
```
Правильно: проверять `null` до распаковки (`counts.getOrDefault("k", 0)`), не смешивать обёртку и примитив в `?:`, держать единый тип ветвей.

## Compare wrappers with equals, not ==

Обёртки — объекты, поэтому `==` сравнивает ссылки, а не значения; из-за кэша маленьких значений результат `==` то «случайно верен», то ложен. Это дом Ch. 49 (контракт `equals`, кэш `Integer`), сюда вынесено ссылкой; практическое правило — сравнивать обёртки через `equals`, а лучше распаковать в примитив и сравнивать `==` уже примитивы.

## Common Mistakes

- Неявная распаковка `null` (см. выше). Правильно: `getOrDefault`/проверка `null`; не смешивать типы в `?:`.

- Обёртка-аккумулятор в цикле.

```java
Integer total = 0;
for (int i = 0; i < 1_000_000; i++) total += i; // миллион лишних Integer
```
  Правильно: примитив `int total`.

- `==` для обёрток вместо `equals` (см. Ch. 49).
